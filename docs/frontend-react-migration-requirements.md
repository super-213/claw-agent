# 前端迁移至 Vite + React + TypeScript 需求文档

## 1. 背景

当前项目是 FastAPI 后端 + 原生 HTML/CSS/ES Module JavaScript 前端。现有前端已经支持：

- 登录、退出和管理员初始化；
- 多会话聊天；
- NDJSON 流式响应渲染；
- 会话复制、删除、共享；
- 会话分支树；
- 后台 Dashboard；
- 技能添加、重载；
- 模型配置；
- 用户管理。

当前原生前端适合小规模功能迭代，但未来计划继续扩展复杂工作台、Dashboard、对话树、编辑器、插件中心和权限系统。随着功能复杂度提升，继续使用手写 DOM、分散状态和全局 CSS 会带来以下问题：

- UI 组件复用困难；
- 状态流转难以追踪；
- 对话流、分支树、权限、配置之间的联动成本上升；
- Dashboard、编辑器、拖拽、图表等复杂交互难以维护；
- 缺少类型约束，API 字段变化容易引入运行时错误；
- 前端测试、构建、代码拆分和生产缓存策略不够系统。

因此需要将前端迁移到 Vite + React + TypeScript，并为未来复杂功能建立可扩展的前端架构。

## 2. 目标

本次迁移目标不是简单换框架，而是建立长期可维护的前端基础。

核心目标：

- 使用 Vite + React + TypeScript 重建前端工程；
- 保留现有 Web 功能，不降低当前用户体验；
- 建立组件化、类型化、模块化的前端架构；
- 与现有 FastAPI 后端继续协作，后端仍作为 API 服务和静态资源托管服务；
- 支持未来复杂工作台、Dashboard、对话树、编辑器、插件中心和权限系统；
- 建立稳定的数据请求、权限判断、流式响应和错误处理机制；
- 引入可持续的构建、测试、格式化和发布流程。

## 3. 非目标

首轮迁移不做以下事项：

- 不将后端迁移到 Node.js 或 Next.js；
- 不重写 FastAPI 业务逻辑；
- 不强制引入 SSR；
- 不改变核心 API 行为，除非现有 API 无法支撑类型化前端；
- 不一次性实现所有未来复杂功能；
- 不引入大型设计系统而不做本地适配；
- 不为了迁移框架而重写 Agent 编排、会话存储或权限后端模型。

## 4. 推荐技术栈

### 4.1 基础框架

- 构建工具：Vite
- UI 框架：React
- 语言：TypeScript
- 包管理：沿用 npm，后续可评估 pnpm

### 4.2 建议依赖

数据请求：

- `@tanstack/react-query`：管理 API 请求、缓存、重试、失效刷新和加载状态。

客户端状态：

- `zustand`：管理当前会话、流式响应状态、UI 面板状态、临时草稿等客户端状态。

路由：

- `react-router-dom`：管理 `/`、`/login`、`/dashboard`、`/settings`、`/plugins`、`/admin` 等页面。

表单：

- `react-hook-form`：处理登录、模型配置、用户管理、技能配置等表单。

图标：

- `lucide-react`：统一按钮、导航、工具栏图标。

图表：

- 首选轻量 SVG/Canvas 自研组件用于当前 Dashboard；
- 复杂图表阶段可评估 `recharts`、`visx` 或 `echarts`。

编辑器：

- Markdown 编辑可评估 `@uiw/react-md-editor` 或自研轻量编辑器；
- 代码编辑可评估 `monaco-editor`，但只在确有复杂代码编辑需求时引入。

拖拽：

- 复杂排序、布局和节点拖动可评估 `@dnd-kit/core`。

测试：

- `vitest`：单元测试；
- `@testing-library/react`：组件测试；
- Playwright：关键流程端到端测试。

样式方案：

- 首选 CSS Modules 或普通 CSS + 明确命名规范；
- 可评估 Tailwind，但需要避免过度工具类堆叠；
- 需要建立设计 token，包括颜色、字号、间距、层级、阴影、边框和动效。

- Vite dev server 运行前端；
- FastAPI 运行 API；
- Vite 通过 proxy 转发 `/api`、`/files`、`/generated` 到 FastAPI。

生产环境建议：

- `npm run build` 输出静态文件；
- FastAPI 挂载构建产物目录；
- 使用 Vite 内容哈希替代当前手动 query string 缓存策略。

## 7. 功能需求

### 7.1 应用壳与导航

需要提供统一应用壳：

- 左侧会话导航；
- 顶部状态栏；
- 主内容区；
- 右侧或底部上下文面板；
- 移动端响应式布局；
- 登录态和未登录态路由隔离；
- 管理员入口按权限展示。

页面路由建议：

```text
/login
/
/dashboard
/plugins
/settings
/admin/users
/sessions/:sessionId
/sessions/:sessionId/tree
```

首轮可以保持 `/` 为聊天工作台，避免改变用户入口。

### 7.2 登录与权限

必须支持现有认证能力：

- 获取初始化状态；
- 首次初始化管理员；
- 登录；
- 退出；
- 获取当前用户；
- 管理员用户管理；
- 普通用户和管理员看到不同导航、按钮和操作入口；
- 未登录访问业务页时跳转登录页。

权限判断要求：

- API 返回 `401` 时统一跳转登录；
- API 返回 `403` 时显示无权限状态；
- UI 按权限隐藏不可用操作；
- 危险操作需要二次确认；
- 权限判断逻辑集中在 hooks、route guard 或权限工具函数中。

### 7.3 会话工作台

需要完整迁移现有聊天页能力：

- 创建新会话；
- 加载会话列表；
- 切换会话；
- 删除会话；
- 复制会话；
- 会话共享设置；
- 展示当前用户；
- 展示当前会话 token 概览；
- 消息列表渲染；
- 空状态；
- 发送消息；
- Shift+Enter 换行，Enter 发送；
- 流式展示助手输出；
- 展示工具调用过程；
- 展示错误状态；
- 自动滚动策略；
- 移动端侧栏打开/关闭。

未来增强需求：

- 会话搜索；
- 会话分组；
- 会话收藏；
- 会话标签；
- 会话批量操作；
- 多标签工作区；

- 会话导入导出。

### 7.4 流式响应

必须保留当前 `/api/chat/stream` 的 NDJSON 流式体验。

前端需要：

- 封装统一 stream client；
- 支持逐行解析 NDJSON；
- 支持 `done`、`error` 和过程事件；
- 事件到 UI 状态的转换必须可测试；
- 支持中途错误展示；
- 支持并发发送保护；
- 支持会话级运行中状态；
- 未来预留取消请求能力。

流式事件建议在前端转换为标准状态：

```ts
type ChatRunStatus =
  | 'idle'
  | 'preparing'
  | 'streaming'
  | 'running_tool'
  | 'saving'
  | 'done'
  | 'error';
```

## 8. 非功能需求

### 8.1 性能

要求：

- 首屏加载不明显慢于当前版本；
- 会话列表和消息列表在中等数据量下保持流畅；
- 大消息、长工具输出和大型分支树需要分层优化；
- Dashboard 图表渲染不能阻塞主线程过久；
- 静态资源使用 Vite 内容哈希缓存；
- 构建产物可按路由或功能拆分。

建议指标：

- 本地开发 HMR 响应小于 1 秒；
- 生产构建主入口 gzip 后保持可控；
- 1000 条消息的会话详情仍可操作；
- 300 个树节点的分支树可正常渲染和交互。

### 8.2 稳定性

要求：

- API 错误统一处理；
- 流式解析错误可恢复；
- 未登录、无权限、会话不存在等状态有明确页面；
- 用户操作失败不破坏当前 UI 状态；
- 长时间流式运行时有运行中反馈；
- 防止重复发送和重复提交。

### 8.3 可维护性

要求：

- TypeScript 严格模式；
- API 类型集中定义；
- 组件职责单一；
- 业务 feature 分目录；
- 样式 token 化；
- 纯逻辑函数单元测试；
- 关键流程端到端测试；
- ESLint 和格式化规则固定。

### 8.4 安全

要求：

- 不在前端持久化完整 API Key；
- 不在日志中输出敏感字段；
- Markdown 渲染必须防 XSS；
- 文件链接只展示后端允许访问的 URL；
- 权限按钮隐藏不能替代后端鉴权；
- 管理员操作需要二次确认。

## 9. API 与类型需求

需要为现有 API 建立 TypeScript 类型：

- `User`
- `SessionSummary`
- `SessionDetail`
- `Message`
- `MessageUsage`
- `BranchNode`
- `BranchTree`
- `Skill`
- `DashboardMetrics`
- `ChatStreamEvent`
- `ShareConfig`
- `ModelConfig`

前端 API 客户端要求：

- 所有请求统一经过 `api/client.ts`；
- 自动处理 JSON；
- 统一处理 `401`、`403`、`404`、`500`；
- 支持 NDJSON stream；
- 支持请求取消；
- 支持类型化响应；
- 不在组件里拼散乱 fetch 逻辑。

如果后端响应字段不稳定，应优先补充后端 schema 或在前端建立窄转换层，避免业务组件直接依赖不稳定结构。

## 10. 迁移策略

建议采用分阶段迁移，避免一次性重写导致功能回归。

### 阶段 0：准备

- 新建 Vite + React + TypeScript 前端目录；
- 配置 npm scripts；
- 配置 Vite proxy；
- 配置 TypeScript strict；
- 配置 ESLint、格式化、Vitest；
- 建立基础路由和应用壳；
- 建立 API client 和类型文件。

验收：

- Vite dev server 可启动；
- 能访问 FastAPI API；
- 能构建生产产物；
- 能由 FastAPI 托管构建产物。

### 阶段 1：认证与应用壳

- 迁移登录页；
- 迁移管理员初始化；

## 12. 风险与对策

### 12.1 迁移范围过大

风险：一次性重写所有页面容易造成长期不可用。

对策：按阶段迁移，优先认证和聊天主流程，Dashboard 和插件中心后移。

### 12.2 API 字段不稳定

风险：前端类型化后会暴露后端响应结构不一致问题。

对策：建立 API 类型和转换层，必要时补充后端响应模型。

### 12.3 流式响应回归

风险：React 状态更新频繁可能导致性能问题或消息拼接错误。

对策：将 stream 解析与 UI 渲染分离，增量事件先进入 reducer，再批量更新 UI。

### 12.4 树图性能问题

风险：大型会话树在 React 中频繁重绘。

对策：树布局纯函数化，节点组件 memo 化，后续引入虚拟化或 Canvas/SVG 分层渲染。

### 12.5 样式迁移不一致

风险：迁移后视觉不一致或退化。

对策：先建立设计 token 和基础组件，再迁移页面，不直接复制零散 CSS。

### 12.6 权限误展示

风险：普通用户看到不该看到的入口。

对策：权限判断集中管理，后端鉴权继续作为最终边界。

## 13. 设计原则

前端设计应遵循：

- 工作台优先，不做营销页；
- 信息密度高但层级清楚；
- 导航稳定，减少跳转成本；
- 复杂操作放在明确面板或弹窗中；
- 图标、按钮、表单、状态提示统一；
- 空状态、加载状态、错误状态完整；
- 支持长文本、长会话和工具输出；
- 移动端可用，但桌面端体验优先；
- 不把装饰性视觉放在功能可读性之前。

## 14. 待确认问题

需要在实施前确认：

- React 前端目录使用 `web-react/`，还是直接替换现有 `web/`；
- 是否继续由 FastAPI 托管前端构建产物；
- 是否需要保留旧前端回滚入口；
- 是否引入 Tailwind，还是采用 CSS Modules；
- Dashboard 图表库首选自研 SVG 还是引入第三方库；
- 插件中心是否只管理现有 skills，还是要规划真正的插件安装机制；
- 是否需要从首轮开始引入 Playwright；
- 是否需要把后端 API 响应补充为 Pydantic schema，便于生成前端类型。

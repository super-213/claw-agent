# 家庭管家事项清单改造计划

日期：2026 年 10 月 23 日  
状态：P0–P3 已实施；2026-10-23 完成回归和双账号浏览器验收  
实施顺序：第 1 项，先完成本文 P0–P3，再实施 010 工作台改版  
范围：家庭成员通过对话记录、查询、修改事项，在家庭工作台查看和处理；当前不做主动通知。

编号调整：本文由原 010 调整为 009；原 009 工作台精简计划调整为 [010 家庭工作台改版计划](010-home-workbench-simplification-proposal.md)。009 已按本计划完成实现；010 整体工作台改版仍待实施。编号与实施先后顺序一致。

## 1. 目标与范围

把 Agent 从“能创建提醒的聊天助手”改造成全家共用的事项管家：记清谁交代了什么、由谁负责、什么时候做、是否重复、这一期是否完成。事项独立于聊天会话持久化，换会话、重新登录和重启服务后仍可查询。

最新抽象采用两个独立维度：**归属空间（个人 / 家庭）× 时间性质（有时效 / 无时效）**。用户通过 `"/ "` 显式选择操作与空间，通过 `"@ "` 选择一名或多名相关成员。这里的“有时效”指有执行日期、截止时间或重复周期，并不表示到期自动删除，也不表示主动通知。

本计划承接 [005 家庭 Agent 需求](005-home-agent-requirements.md) 中的成员协作目标。本文不依赖 010 的导航、首页精简或视觉重构；先在现有界面中完成可用的备忘功能，再由 [010 家庭工作台改版计划](010-home-workbench-simplification-proposal.md) 复用这些业务能力整理界面。本轮以本文的范围为准，不实施 005 中的主动推送与消息触达部分。

### 1.1 必须覆盖的使用场景

| 用户表达 | 系统实际动作 | 用户后续如何看到 |
| --- | --- | --- |
| 帮我记下：买牛奶、交电费、预约体检 | 拆成三条由当前用户负责的未完成事项，无日期也能保存 | 询问“我的备忘清单”或打开工作台“我的事项” |
| 列出我的备忘清单 | 查询当前用户负责的事项，默认未完成，包含无日期事项 | 回答以真实记录为准，支持查看已完成 |
| 把买牛奶标记为完成 | 找到有权操作的对应事项，完成当前实例 | 对话与看板同步更新，保留完成历史 |
| 明天告诉小明要交电费 | 记录一条小明负责的明日事项，保留交代者；不发送消息 | 小明询问“明天我要做什么”或打开其工作台时可见 |
| 这件事每周都要做，帮我记录下 | 找到当前明确指向的事项，设置每周重复，保留每期完成状态 | 询问或打开工作台时显示本周事项 |
| 每周三让爸爸倒垃圾 | 记录爸爸负责、每周三到期的周期事项 | 爸爸的“本周事项”与家庭有权查看的清单 |
| 家里要买牛奶，谁方便谁买 | 创建家庭共享、暂未认领的事项 | 全家可见；成员可认领并完成 |

表中自然语言表达继续作为兼容入口；首版主入口改为第 1.3–1.4 节的显式命令。普通聊天中的“每周六要大扫除”可能是个人安排，也可能是家庭安排，不再仅凭这句话直接写入家庭空间。

“明天告诉小明”在本轮的产品语义是“记入小明的明日事项”。创建后明确回复：“已记入小明的明日事项，他询问或打开工作台时可以看到。”不能回复“已经告诉小明”“明天会通知小明”。未来事项可提前在“全部/明日”中查看，明天自动进入今日视图，无需后台发送动作。

### 1.2 本轮交付边界

- 实现个人事项、指定成员事项、家庭共享事项、批量记录、查询、编辑、认领、完成、撤销完成、取消、周期记录和历史。
- 实现个人/家庭两类空间，有时效/无时效两类备忘，以及 `"/ "` 命令选择和多成员 `"@ "` 指派。
- 支持单次日期、无日期事项，以及每周重复；日期采用家庭时区，默认沿用 `Asia/Shanghai`。
- 对话与工作台调用同一业务服务，使用同一份结构化数据。
- 不新增主动消息、Web Push、邮件、短信、通知队列、送达状态、催办或后台调用模型。
- 不执行事项本身。例如“交电费”只记录任务，不接入支付；“预约体检”只记录任务，不代为预约。
- 首版继续服务当前单家庭部署，保留 `household_id` 字段；不扩展多家庭组织、访客和复杂审批流程。

### 1.3 显式命令：空间、性质与成员分别选择

建议使用以下命令名称；输入 `"/ "`（斜杠后跟一个半角空格）触发显式工具调用命令入口，展示可搜索工具菜单，选择后显示固定的“空间 / 备忘性质”标签。四个入口在实现上组合为两个性质和两个空间，不分别维护四套业务逻辑。

| 命令 | 归属空间 | 时间性质 | 示例 |
| --- | --- | --- | --- |
| `/ 日程` | 当前用户的个人空间 | 有时效 | `/ 日程 每周三锻炼` |
| `/ 备忘` | 当前用户的个人空间 | 无时效 | `/ 备忘 买牛奶、交电费、预约体检` |
| `/ 家庭日程` | 家庭空间 | 有时效 | `/ 家庭日程 每周六大扫除` |
| `/ 家庭备忘` | 家庭空间 | 无时效 | `/ 家庭备忘 补充洗衣液` |

- `"/ "` 菜单是用户操作入口；真正执行由后端注册的结构化工具完成。不能只把 `/ 日程` 拼入提示词后仍由模型猜类型。
- `/ 日程` 和 `/ 家庭日程` 必须提供可解析日期或周期；缺少时询问补充，不能悄悄降级为无时效备忘。
- `/ 备忘` 和 `/ 家庭备忘` 不生成日期、周期或逾期状态。正文出现时间表达但用户尚未选择日程时，保留为待补充草稿并提供“一键转日程 / 仅作为文字保存”，不擅自转换。
- 无时效不等于不会完成：“买牛奶”即使没有截止时间，也能勾选完成。首版备忘默认按可完成事项记录；纯信息如“备用钥匙在玄关抽屉”可在创建卡显式选择“信息记录”，仅编辑/归档，不显示完成按钮。
- 查询、完成仍可自然语言表达，工作台也提供按钮。直接说“帮我记下……”时先返回可选择的空间和性质草稿；仅在当前输入框已有明确选中的标签时沿用，不凭语义默默替用户选家庭空间。
- 单次事项转周期、无时效转日程、移动空间均为显式修改；保留原 ID和历史，避免重复保存。

### 1.4 命令前缀的空格属于语法

- 工具调用前缀严格为 `"/ "`，成员指定前缀严格为 `"@ "`，第二个字符均为半角空格 `U+0020`；不能把空格仅当作文档排版。
- 完整示例是 `/ 日程 每周三锻炼`、`/ 家庭日程 @ 爸爸 @ 妈妈 每周六大扫除`。命令名称仍为本计划建议的工具显示名称。
- 单独的 `/`、`@`，以及 `/日程`、`@小明` 不触发上述显式调用入口；普通文本仍可继续编辑。
- 解析器在输入起始处识别 `"/ "`，在合法正文标记边界识别 `"@ "`；不对 URL、路径、邮箱、引用内容或代码示例做全局替换。前后端使用相同的语法约束。
- 请求保留原始输入和已解析的结构化调用，不能先删除前缀后的空格再按另一套命令语法执行。工具与成员标签选中后仍绑定稳定 ID。

### 1.5 `"@ "` 指派与多人协作

输入 `"@ "`（@ 后跟一个半角空格）打开家庭成员候选，选择后形成绑定 `member_id` 的成员标签，支持多选和取消。用户看到姓名，后端收到稳定 ID；正文中普通邮箱或未选中的 `@文字` 不自动成为指派。

```text
/ 日程 @ 小明 明天交电费
/ 家庭日程 @ 爸爸 @ 妈妈 每周六大扫除
/ 家庭备忘 @ 小明 @ 小红 补充洗衣液
```

- **空间决定记录属于哪里、谁可见；`"@ "` 决定谁负责。** 家庭空间里的 `@ 小明` 不会将记录移成个人私有，也不会把家庭空间限制为仅小明可见。
- 无 `"@ "` 的个人事项默认由自己负责；无 `"@ "` 的家庭待办默认未认领，不自动给全家每人派一份。
- 指派给他人的个人空间事项，由交代者与被指派者可见；对方个人工作台的“指派给我的”显示同一条记录的引用，不开放交代者整个个人空间。
- 多个 `"@ "` 表示多个负责人。首版默认“每人都要完成”，分别保存各自完成状态；创建卡和回执明确显示这一规则。若希望“任一人完成即可”，在创建卡显式切换，不让模型从“大扫除”等词猜测。
- 家庭任务只存一条权威记录，在各负责人个人视图中投影展示；任一视图完成后其他视图同步，不复制为互不相关的多份数据。
- 信息记录也可 `"@ "` 指定相关成员，但不产生完成进度或通知；其归属空间和可见范围仍按所选空间处理。
- `"@ "` 仅用于产品内指派或关联，当前不会发送消息，也不表示对方已收到或读过。

以下表格保留实施前的代码基线；最终交付与验收见第 12 节。

| 模块 | 当前实现 | 本轮改造 |
| --- | --- | --- |
| [home_service.py](../services/home_service.py) | `household()` 保存家庭配置，成员默认是空数组；提醒有 `recipients`、`trigger`、状态与 JSON 持久化 | 补全成员绑定；新增独立事项服务，复用存储方式 |
| [intent_router.py](../services/intent_router.py) | 规则优先、LLM 意图检测兜底；家庭动作包含库存与创建提醒 | 事项意图进入统一执行链，支持查询、完成和多轮补充 |
| [builtin_tools.py](../agent_runtime/builtin_tools.py) | 已有原生工具注册，但没有事项专用工具 | 注册家庭成员查询与事项操作工具 |
| [orchestrator.py](../core/orchestrator.py) | 可传入 `user_id`；完成 Run 后保存目标和结果为会话记忆 | 将认证身份绑定工具执行，保留结构化事项引用 |
| [memory.py](../agent_runtime/memory.py) | 会话/用户文本记忆，关键词检索 | 继续用于背景信息；不作为事项清单的权威数据源 |
| [web_app.py](../web_app.py) | 两种聊天入口都先调用意图路由；已有提醒、通知和家庭 API | 新增事项 API，两种聊天入口行为一致 |
| [HomePage.tsx](../web-react/src/features/home/HomePage.tsx) | 可展示提醒并完成、延后、取消；还包含通知配置 | 增加真正的事项看板，按日期、成员、状态查询 |

需要优先解决的具体问题：

1. 无日期的“记下几件事”没有独立数据模型，无法可靠查询和逐条完成。
2. 现有自然语言创建提醒通常将收件人固定为当前用户，未解析“小明”“爸爸”等成员指向。
3. `HybridIntentRouter.route()` 只接收当前文本、用户和 session ID，没有明确的结构化上一事项引用，难以处理“这件事”。
4. `complete_reminder()` 直接把整条提醒设为 `completed`；周期提醒会因此停止继续处理，无法表达“这周做完，下周继续”。
5. 现有提醒查询/详情/修改及通知读取主要检查登录，没有完整的逐条成员权限限制；增加个人事项前必须补上服务层校验。
6. 工作记忆仅保存目标和结果，且检索依赖词语重合，不能保证“列出我的清单”返回完整数据。
7. 现有 `_home_scheduler_loop()` 会主动处理到期提醒。本轮事项不进入这条发送链。
8. 通用 `file_read` 允许读取项目目录内文件，现有 Shell 沙箱也不能直接作为成员数据隔离边界；仅给事项 API 加权限仍可能绕过专用工具读取原始数据。

## 3. 业务规则：谁的事、什么时候做、怎样算完成

### 3.1 成员与称呼解析

复用现有 `UserStore` 账号，给 `household.members` 增加稳定成员 ID、绑定账号、显示名称和称呼。首版可操作成员必须绑定有效账号；未绑定成员不能被描述为“能在自己的工作台看到”。

建议结构：

```json
{
  "member_id": "member_xiaoming",
  "user_id": "u_xiaoming",
  "display_name": "小明",
  "aliases": ["明明"],
  "status": "active"
}
```

- “我/我的”从当前请求的认证身份解析，不能接受模型自报用户身份。
- 优先匹配成员 ID、唯一姓名和当前说话者配置的称呼，再匹配家庭通用别名。
- “爸爸/妈妈”支持按说话者保存称呼映射，例如 `speaker_member_id + alias -> target_member_id`；不假定所有人的“爸爸”都指同一人。
- 命中多人时返回候选供选择；找不到成员时保存未执行草稿并询问，不创建假账号、不分配给当前用户冒充目标成员。
- 成员改名不改变历史归属；账号停用后历史保留，新分配被拒绝，未完成事项显示“负责人已停用”以便重新分配。
- 首次启用由管理员把现有有效账号绑定为家庭成员，不能在迁移时默默给全部账号授予家庭访问权限。

### 3.2 默认归属与可见范围

以用户选中的命令/空间标签和成员标签为准，执行以下规则：

| 显式选择 | 负责人 | 默认可见成员 |
| --- | --- | --- |
| 个人命令，无 `"@ "` | 当前用户 | 当前用户 |
| 个人命令，`"@ "` 一人或多人 | 指定成员 | 交代者与指定成员 |
| 家庭命令，无 `"@ "` | 可完成事项暂未认领；信息记录无负责人 | 当前家庭全部有效成员 |
| 家庭命令，`"@ "` 一人或多人 | 指定成员 | 当前家庭全部有效成员 |

区分 `space_id`（记录归属）、`created_by`（谁交代）、`assignee_ids`（谁负责）和 `visibility`（谁能看）。个人空间拥有者只能是当前用户，不能通过任意传入空间 ID 写进别人的空间；给别人分配通过 `"@ "` 和个人视图引用实现。

- “我的事项”默认指自己负责的事项；“我交代的”查询自己创建并委派给别人的事项。
- “全家事项”查询明确共享给全家的事项；不得把所有人的个人事项拼成家庭列表。
- 家庭未认领事项单独展示，不能因没有负责人而消失；认领成功后仍保持家庭可见。
- 跨成员委派默认允许有效家庭成员使用，保留交代者；这是本产品内记录指令的能力，无需另加一轮发送确认。
- 负责人可完成、撤销完成自己的份额；交代者可编辑内容、执行日期、重新分配和取消自己交代的事项。多人事项不允许某一负责人直接改掉全体日期。
- 家庭未认领事项由成员先认领，再完成；其他成员仅可查看已认领事项，不能替负责人勾选。
- 周期规则、共享范围和负责人由交代者修改；负责人可暂停自己的后续参与并留下原因，不能替其他负责人停止整个系列。
- 技术管理员的账号管理权限与日常事项权限分开；首版事项接口按上述参与者规则执行。现有管理员可查看会话的机制仍然存在，共享会话中的内容可见性另见第 6 节。

所有列表、详情、统计、搜索、工具和历史接口先做对象权限过滤，再分页/计数；传入别人的 ID 不等于获得权限。非可见对象统一返回未找到，可见但无操作权限返回禁止操作。

### 3.3 时间与周期语义

- 无时效备忘没有日期，`due_date=null`；信息记录也没有完成期限。选了日程却缺少时间时保留草稿并补充，不能以空日期作为已生效日程保存。
- “明天”：按请求接收时的家庭当地日期计算；本轮只需要日期，不追问几点。
- “明天 8 点做”：允许保留明确时间，供查询和看板展示，不触发通知。
- “每周做”：以家庭时区周一至下周一为一个周期，每周一件，整周内均可完成；不追问星期几或几点。
- “每周三做”：每周一个实例，周三为截止日期，不默认产生提醒时间。
- “这件事每周做”：沿用明确指向的事项内容、负责人和范围；原本明确的周期内执行时间可以继承，回执必须展示。没有时间就按整周一次。
- “下周开始每周做”：保留开始日期，本周不生成待办。
- 用户指定的过往日期不偷偷改成未来日期；记录为逾期事项并在回执说明。
- 日期保存为当地 `YYYY-MM-DD`，明确时间保存带时区的时间点；跨日和周期计算统一使用任务所属时区，前端不凭浏览器时区重算“今天”。

本轮必须正确处理每周重复。每日、每月和复杂 RRULE 属于后续扩展；遇到尚不支持的规则返回明确说明并保留待补充草稿，不把它当作已生效的周期任务。

### 3.4 单次事项与周期事项的完成规则

周期事项拆为“系列定义”和“各期实例”。例如“每周买牛奶”只有一个系列，但 10 月 19 日这一周、10 月 26 日这一周分别有独立实例。

- “完成买牛奶”：单次事项完成其唯一实例；周期事项默认完成本期实例。
- “这周做完了”：本期完成，下周实例仍会出现。
- “这周不用做”：跳过本期，后续周期继续。
- “以后不用做了”：停止系列，保留过去历史；停止时将尚未完成的实例取消并记录原因。
- “暂停每周买牛奶”：暂停后不再产生新的实例，已有未完成实例保留；恢复从当前周期继续，不补造暂停期间实例。
- 已完成实例可撤销完成；重复点击完成返回原结果，不增加多份完成记录。
- 逾期是根据日期和实例状态计算的展示属性，不新增一个与 `open/completed` 冲突的存储状态。
- 上期未完成不阻止本期出现。看板默认展示本期与历史未完成数量，可展开历史，不能把所有历史堆满首页。
- 多负责人实例保存逐人成果。`completion_mode=all` 时所有应完成人员都完成才聚合为完成；`any` 时任一负责人成为完成者即结束本期，其余份额标记为不再需要执行，不能伪造为各自已完成。
- 信息记录不创建执行实例，不参与待办/完成率/逾期统计；在空间的备忘列表中持续展示，直到归档。

## 4. 数据模型与存储

### 4.1 继续采用本地 JSON，事项集中保存

首版沿用项目文件存储，在配置的家庭数据目录新增 `tasks.json`，不引入外部数据库。将事项定义、周期实例、操作去重信息与必要的变更记录放在同一份快照中，通过一次原子替换提交，避免多个文件只有部分写入成功。

```text
.data/home/
├── household.json       # 扩展账号绑定和称呼
├── tasks.json           # 新增：事项、实例、操作去重、变更记录
├── reminders.json       # 旧提醒数据，保留并用于迁移
├── schedules.json       # 旧周期配置，保留并用于迁移
└── backups/             # 迁移前快照与日常备份
```

根对象含 `schema_version`、`revision`、`tasks`、`occurrences`、`operations`、`events`。不得仅在某条会话消息中保存任务。

每个成员一个逻辑个人空间，当前家庭一个家庭空间，统一保存在同一仓储，不按成员复制账本。个人空间的授权来自账号绑定，家庭空间的授权来自有效成员关系；个人工作台同时可展示自己空间的条目以及其他空间中指派给自己的条目。

### 4.2 事项定义 Task

| 字段 | 含义 |
| --- | --- |
| `id / household_id` | 稳定事项 ID、家庭 ID |
| `space_id / space_type / space_owner_id` | 个人或家庭空间；个人拥有者为成员 ID，家庭拥有者为家庭 ID |
| `temporal_type / actionable` | `timed / undated`；是否可完成，首版日程固定可完成、无时效备忘可显式选信息记录 |
| `title / description / category` | 原始事务内容；可选购物、家务、账单、个人等分类 |
| `created_by / assignee_ids / related_member_ids` | 交代者、多位负责人；信息记录的 `"@ "` 保存为相关成员，不伪装成执行人 |
| `completion_mode` | `all / any`；多人可完成事项默认 `all`，信息记录为空 |
| `visibility` | `participants` 或 `household`；个人事项参与者为交代者与指定成员，家庭事项全家可见 |
| `lifecycle` | `active / paused / archived`；与完成状态分开 |
| `timezone / recurrence / starts_on` | 时区、重复规则、开始日期；单次事项 `recurrence=null` |
| `version / created_at / updated_at` | 乐观锁版本、时间 |
| `source` | 原始指令、说话者、session/node/run 引用；来源会话删除不删除事项 |

每周规则示例为 `{"frequency":"weekly","interval":1,"week_start":"MO","weekday":null}`；`weekday=null` 表示周内任选时间完成，指定周三则为 `WE`。规则有修订号，修改规则仅影响尚未开始的周期，已完成历史保持原快照；“本周也改”需显式操作当前实例。

单次事项转为周期事项时，在同一事务内将原单次实例归入其日期所在的首个周期；无日期则归入当前周期，保留原完成状态与来源引用。原日期为过去或未来时，回执明确首次周期，必要时询问开始日期；不能同时留下原单次待办和重复的首期待办。

补充约束：`undated` 不允许保存生效的日期或周期，`timed` 至少有一个日期/周期；信息记录不能调用完成工具。空间类型、性质和成员以结构化标签为准，模型不得覆盖。空间切换需同时校验目标空间权限、展示受众变化并记录版本；不能仅改一个 `visibility` 字段绕过。

### 4.3 事项实例 Occurrence

| 字段 | 含义 |
| --- | --- |
| `id / task_id / period_key` | 实例 ID、系列 ID、周期标识；单次为 `once`，周周期使用当地周一日期 |
| `period_start / period_end` | 周期起止，左闭右开；单次可为空 |
| `due_date / due_at` | 可空截止日期、可选明确时间；整周事项截止日是该周周日 |
| `status` | `open / completed / skipped / cancelled` |
| `assignee_ids / title_snapshot / rule_revision / completion_mode` | 本期多成员归属、内容/规则和完成模式快照，保护历史语义 |
| `member_progress` | 按成员保存状态、完成者与完成时间；并发更新不得覆盖其他人的进度 |
| `completed_by / completed_at / version` | 谁在何时完成、实例版本 |

周期实例以 `(task_id, period_key)` 唯一；修改未来规则不能借修订号在同一期生成第二份任务。单次事项也使用实例，以统一完成、恢复和历史接口。

多成员暂停/重新分配保留生效日期和参与者变更历史，不重写过往周期。最后一位负责人暂停后显示“无执行人”，不自动判定全员完成；每期的分母按该期有效参与者确定。

### 4.4 并发、幂等与备份

- 所有读改写在同一事项仓储中完成；必须锁住完整的“读取—校验—修改—保存”区间，不能只锁最后写入。
- 使用线程锁配合本地跨进程文件锁，临时文件名使用随机 ID，并通过 `os.replace` 原子替换；首版部署与测试覆盖 macOS/Linux 本地文件系统。
- 修改请求携带 `expected_version`；两人同时认领、完成与取消竞争等情况返回 `version_conflict`，刷新后重试。
- 一个批量记录操作整体提交。某一条参数无效时整批不落库，返回错误及已解析草稿，不产生“说记了三条，实际只有两条”。
- HTTP `request_id` 由客户端为一次用户提交生成，Run 重试沿用；模型的多个合法操作增加不同 `operation_index`。服务端按认证用户、请求、操作序号和规范化参数保存结果；同键不同参数拒绝。
- 不仅依赖 `tool_call_id` 去重：恢复 Run 时模型可能重新生成调用 ID。
- 变更事件与业务数据同快照提交；现有 `activity_log.jsonl` 可做展示镜像，不能成为恢复任务的唯一依据。事件访问同样遵守事项权限，旧负责人失去访问权后不能通过事件正文读到新的私有内容。
- 加入现有家庭备份流程，支持 JSON 导出；保留去重记录的窗口覆盖最长请求重试/恢复期，归档与压缩不能破坏该窗口内的幂等。

## 5. 无通知的周期计算与看板投影

本轮无需后台定时调用 LLM，也不需要发送调度器。每次查询事项、读取看板或完成周期任务时，由本地 `TaskRecurrenceService` 根据当前时间计算应存在的周期，在存储锁内幂等补齐实例。

1. 新建每周事项时生成当前有效周期实例；未来开始的系列暂不生成当前待办。
2. 打开工作台、Agent 查询或执行完成操作前，将相关且有权访问的系列推进到当前周期。
3. 同一次查询用固定的家庭当前时间生成列表和汇总，避免跨日时数量与列表不一致。
4. 未来 7 天/明日查询可以生成不落库的预测投影，明确标记 `projected=true`；对未来实例执行操作时再在事务中落库。预测查询不能推进系列的当前周期游标。
5. 重启或长期无人访问后补齐遗漏周期，每期一个实例，历史未完成可按周期查询；首次启用从 `starts_on` 起算，不补造任务创建前的历史。
6. 为长时间离线设置分批补齐上限，并记录推进游标；查询返回 `history_complete/next_cursor`。当前周期必须优先可见；历史未补齐时不返回看似精确的历史总数或漏报“没有逾期”，显示“历史整理中”并可继续加载。

工作台打开时首次加载，操作后刷新，并在页面可见时每 60 秒及窗口重新聚焦时刷新。这样跨日、跨周能更新页面；页面关闭期间不做任何主动触达。

## 6. Agent 接入：工具执行、指代与多用户上下文

### 6.1 统一执行路径

```text
用户对话 / 工作台操作
  → "/ " 命令选择空间和性质，"@ " 选择成员，或工作台表单显式选择
  → 服务端解析认证用户、家庭成员、会话及当前时间
  → Agent 理解剩余正文中的事项和时间，保留显式选择
  → FamilyTaskService（权限、时间、幂等、状态转换）
  → TaskStore 原子持久化
  → 结构化结果
  → Agent 回答 / 看板刷新
```

Agent 通过原生 Function Calling 使用下列工具；表单 API 直接调用相同服务。将原计划中的通用创建工具拆成两类性质明确的工具，内部仍调用同一个 `FamilyTaskService`。现有意图路由只提供解析提示和候选，不另写一套直接修改任务文件的逻辑。

| 建议工具 | 职责 |
| --- | --- |
| `family_member_resolve` | 将姓名、称呼解析为可用成员或候选列表 |
| `family_timed_memo_create` | 创建有时效事项；日期或周期必填，不能创建无时效记录 |
| `family_undated_memo_create` | 创建无时效备忘；不接受日期或周期，可显式选择可完成事项或信息记录 |
| `family_task_list` | 按我的、我交代的、家庭共享、日期、状态查询，返回可操作 ID |
| `family_task_get` | 查询具体事项、当前实例与历史 |
| `family_task_update` | 编辑日期、内容、归属或周期；明确 `this_occurrence / future` 范围 |
| `family_task_claim` | 认领家庭未分配事项 |
| `family_task_complete / family_task_reopen` | 完成、撤销完成指定实例 |
| `family_task_skip / family_task_cancel` | 跳过一期或取消单次实例 |
| `family_task_pause / family_task_resume / family_task_archive` | 暂停、恢复或停止周期系列 |

工具 Schema 不提供可伪造的 `actor_id`、任意家庭 ID或权限开关。`assignee_ids` 是目标成员参数，仍需服务层验证。

前端提交 `invocation={command, space_type, temporal_type, mentions, actionable}`，其中 `mentions` 包含绑定后的成员 ID和标签位置。后端规范化并绑定到本次请求：`/ 日程` 只允许调用日程创建工具，`/ 备忘` 只允许调用无时效工具；空间和已选成员从该上下文注入，模型参数与显式选择冲突时拒绝并要求修正。服务端仍需验证账号、成员和空间权限，不能把前端标签当作授权凭证。

主模型只负责拆分正文、提取日期和补充说明，不再判断用户已经明确选择的空间或时间性质。自然语言兼容入口缺少这些选择时先返回草稿；展示草稿不等于已执行。修改时间性质、移动空间或补充 `"@ "` 必须产生新的显式操作元数据。查询与完成可使用自然语言，但仍调用受权限约束的结构化工具。

当前工具 handler 接收模型参数，且 Web 使用共享 registry。实现时为每次 Run 创建带不可变执行上下文的任务工具绑定，或显式扩展执行器传入上下文；不得把“当前用户”写进全局 registry 的可变字段。恢复 Run 时重新认证并校验当前用户及最新对象权限。CLI 未建立成员身份时不开放跨成员写工具。

### 6.2 “这件事”与补充参数

- 保存最近操作的结构化引用，维度至少包含 `session_id + active branch + speaker_member_id`，记录任务/实例 ID、版本、用户消息 ID与返回时间。
- 当前输入框可携带从看板选择的 `task_ref`；服务端验证后使用，不能仅信任客户端传来的标题。
- 最近操作唯一时，“这件事每周做”修改该事项；上一轮新建三件事则询问指哪一件，支持“第一件”“买牛奶那件”。
- 搜索范围先限定为有权操作、符合状态的事项。相同标题有多条时显示负责人、日期与短 ID，不能随意完成第一条。
- 切换分支、切换用户、来源消息被删除或引用失效时重新解析；不借用另一个用户上轮的“这件事”。删除会话不会删除已落库事项。
- 缺少成员或事项指向时，保存带有效期的待补充草稿；用户下一句补充后再执行。读取待补充草稿也必须绑定说话者和分支，禁止抢答另一个人的草稿。
- 未选中候选的纯文本 `@ 小明` 返回待解析标签，不直接写入；同名候选必须让用户选定。编辑正文时删除成员标签应同步移除结构化成员引用，不能留下“屏幕看不见但仍指派”的参数。

### 6.3 共享聊天与记忆边界

事项权限与聊天共享权限是两套边界。不能因为某人能进入共享会话，就让他查询其中其他人的个人事项。

- 私有事项详情只回写到受众受限的个人会话；首版不扩展单条消息 ACL 时，在共享会话中提示进入个人会话查看，避免把私有查询结果永久写到共享历史。
- 家庭共享事项可在共享聊天中直接操作。参与者事项只有在会话全部可见成员均有事项读取权限时才允许回写详情，否则转个人会话。
- 共享受众后续扩大会暴露历史正文：含私有事项结果的会话禁止扩大共享范围，除非另行实现历史脱敏/逐条消息权限；管理员原有会话管理权限须在产品说明中保留准确边界。
- `MemoryStore` 不负责列清单或统计。Agent 查询时必须调用事项工具，不能仅凭工作记忆回答“都做完了”。
- 工作记忆可保留事项引用，但后续使用前重新查权限与状态；旧摘要不是当前状态或授权证明。
- 在家庭成员使用的工具集合中，禁止通用文件工具直接读取配置的家庭数据目录、用户数据、会话和备份；按解析符号链接后的真实路径校验，不能只判断是否在项目根目录内。家庭模式默认不暴露通用 Shell；需要保留其他技能的命令能力时，必须使用隔离的运行环境且不挂载这些数据，不能依赖提示词或命令字符串黑名单。未经授权的原始数据也不能进入模型上下文或生成文件下载入口。
- 批量保存成功后回执列出实际保存的条目、负责人、日期或周期。工具返回失败时不得声称已记录、已完成或已告知他人。

## 7. API 与家庭工作台

### 7.1 建议新增接口

```text
GET    /api/home/members                         # 当前家庭成员和称呼候选
PATCH  /api/home/members/{member_id}             # 管理员维护绑定、别名
GET    /api/home/tasks                           # 事项列表，分页与筛选
POST   /api/home/tasks                           # 单条或批量创建
GET    /api/home/tasks/summary                   # 当前用户可见事项的汇总
GET    /api/home/tasks/{task_id}                 # 定义、实例与历史
PATCH  /api/home/tasks/{task_id}                 # 修改内容/未来规则
POST   /api/home/tasks/{task_id}/claim
POST   /api/home/tasks/{task_id}/pause
POST   /api/home/tasks/{task_id}/resume
POST   /api/home/tasks/{task_id}/archive
PATCH  /api/home/tasks/{task_id}/occurrences/{occurrence_id}
POST   /api/home/tasks/{task_id}/occurrences/{occurrence_id}/complete
POST   /api/home/tasks/{task_id}/occurrences/{occurrence_id}/reopen
POST   /api/home/tasks/{task_id}/occurrences/{occurrence_id}/skip
POST   /api/home/tasks/{task_id}/occurrences/{occurrence_id}/cancel
```

列表支持 `view=mine|delegated|household`、`space_type`、`temporal_type`、`actionable`、`status`、`assignee_id`（查询某一位负责人）、`due_from/due_to`、`recurring`、`query`、`cursor`。`summary` 在动态 ID 路由前注册。`PATCH` 当前实例只编辑当前日期/内容；修改系列规则使用事项级接口，响应明确作用范围。创建 API 必须使用判别模型校验 `timed/undated` 两类输入，不能比工具入口更宽松。

列表和汇总响应携带 `as_of`、`timezone`、`revision`。工具输出、页面和统计使用相同过滤规则；聊天操作成功后返回 `task_changed` 事件及 ID/revision，前端使对应查询失效并重新加载。并发、缺参、歧义与无权限使用结构化错误码，而非仅返回一段报错文字。

### 7.2 看板展示

本阶段在现有工作台增加备忘入口和可独立复用的事项模块，不等待 010 首页改版。模块内部提供“个人空间 / 家庭空间”切换，每个空间有“日程 / 备忘”分栏；不在此阶段整体调整应用主导航、拆除全站布局或完成视觉重构。个人视图再区分“自己的 / 指派给我的 / 我交代的”，跨空间投影必须显示来源，避免误认为有多份任务。本轮至少交付以下可用视图：

- **我的事项**：今天、逾期、无日期、本周；无日期事项有独立入口和数量。
- **我交代的**：显示负责人和完成状态，便于查看“明天让小明交电费”。
- **家庭共享**：未认领、已认领、已完成，可按成员筛选。
- **周期事项**：本期状态、下期预览、暂停状态、完成历史。

事项行展示标题、负责人、交代者、日期/周期、状态及完成按钮。周期完成按钮写“完成本周”或“完成本期”；停止重复放在详情操作中，防止误把整条系列关闭。

输入框支持 `"/ "` 搜索菜单、成员候选、多人标签与键盘选择；命令选中后固定展示空间和性质，可显式切换。多人待办显示“已完成 1/2”与当前完成模式；信息记录显示编辑/归档，没有完成按钮，也不挤入今日待办。

首页仅展示有限条待处理事项和“查看全部”。没有权限的事项不参与首页数量。暂无数据、查询失败、保存中、并发冲突和历史补齐中都有明确状态；前端保存失败时回滚勾选状态。

本轮页面不展示通知权限、VAPID、推送配置或送达率。旧通知历史如需保留，放在兼容入口，不混入事项完成统计。

## 8. 旧提醒与数据迁移

### 8.1 旧发送链的处理

产品本轮按“不主动通知”运行。给旧 `_home_scheduler_loop()` 的启动增加明确功能开关，本轮部署默认关闭旧提醒发送；新事项始终不接入 `process_due_reminders()`。不删除旧推送订阅与历史数据，不新增发送实现。

旧 `/api/home/reminders` 和 `/api/home/schedules` 在迁移后成为兼容适配入口，读写映射到同一事项服务；不再同时写旧文件和新文件，也不能继续触发发送。不能立即映射的旧操作返回明确兼容提示。通知发送相关入口在此产品模式关闭或隐藏，避免界面仍承诺会提醒。

### 8.2 迁移规则

1. 先备份 `household.json`、`reminders.json`、`schedules.json` 和相关日志；输出预演报告，不修改原数据。
2. 明确迁移来源 ID，建立 `legacy_type + legacy_id -> task_id` 映射，重复执行不重复创建；疑似同名记录不能靠标题自动合并。
3. 将账号 ID 映射为成员 ID。缺失成员进入管理员可见的待核对记录，不把数据默认为全家公开。
4. 单次提醒迁移为单次事项。`completed` 映射已完成，`cancelled` 映射取消；`sent/failed/snoozed/scheduled` 均不代表事情完成，迁移成未完成并保留旧发送状态作为历史说明。
5. 可识别的每周 RRULE 迁移为周期系列，保留明确的星期和时间；`paused` 保留暂停。旧周期若整体为 `completed`，无法判断用户曾完成一期还是停用系列，先归档为待核对，不能自动恢复每周任务。
6. 多收件人旧记录迁移为一条多成员记录和逐人成果，保留原记录 ID，暂按 `all` 列为待核对，不伪造已完成人员；如果旧语义本来是任意一人完成，由用户核对后切换 `any`。没有可靠共享声明时保留参与者可见，不默默公开到家庭空间。
7. 未支持的日/月/复杂规则以及无法确定归属的数据保留在待核对视图，不启用通知、不宣称已经恢复周期计算。
8. 首版不根据旧发送日志推断每期是否做完，只建立迁移时的有效实例；更早执行历史未知要明确显示，不能伪造完成记录。
9. 迁移后校验条数、成员、状态和映射完整性，再切换读写；回滚前暂停写入并导出切换后新增/修改的数据，不能简单恢复旧备份而丢失新指令。

## 11. 首版明确采用的产品决策

1. 当前不主动通知，所有事项通过主动询问和看板查看。
2. 使用“个人/家庭空间 × 有时效/无时效”模型；通过 `"/ "` 显式选择，普通聊天缺少选择时先形成草稿。
3. “明天告诉某人”落为对方明日事项，记录交代者，不声称已送达。
4. “每周做”无需额外指定时间即可记录；完成一期与停止重复是不同动作。
5. 事项以专用结构化存储为准，聊天历史和记忆只辅助理解。
6. 首版优先复用账号、JSON、本地部署与原生工具体系；未来如增加主动通知，再基于事项实例扩展独立通知模块。
7. `"@ "` 指定一名或多名负责人，不能覆盖所选空间；各个人视图引用同一权威记录，多人默认各自完成，可显式切为任一人完成。
8. 无时效备忘也可以完成；纯信息记录由用户显式选择，只编辑/归档，不纳入待办完成率。

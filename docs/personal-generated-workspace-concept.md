# 稳定主界面与个人生成工作区：概念计划

日期：2026 年 10 月 29 日  
状态：概念探索，未排期，未承诺实施  
范围：讨论在现有 Claw Agent 中引入个人生成工作区的产品形态、架构边界与验证路径。本文不代表现有功能，也不是必须执行的实施清单。

## 概念来源

本文承接文章[《未来，每个人看到的界面都不一样》](https://blog.zhihaojiang.com/2026/10/29/generative-ui-personal-interface-agent/)中的设想：数据与公共规则由可信服务维护，个人 Agent 根据用户目标组合能力，生成并持续维护自己的界面与工具。

在本项目中的具体方向是：**保留稳定主界面，为每个用户提供独立的生成工作区。** 用户从需求出发，让项目内的 Agent 构造工作台、数据视图和交互模块；有用的结果可以保存、反复使用，并通过对话继续修改。

目标不仅是调整颜色、顺序和尺寸，也包括生成现有组件尚未表达的新界面与交互。布局组合可以作为起点，不能代替完整方向。

## 产品形态

### 稳定主界面

现有聊天、家庭业务页面、登录与设置等构成稳定入口。生成工作区作为其中一个入口或区域，具体导航位置尚未确定。

主界面承担身份、权限提示、模块管理、预览与版本切换等宿主职责。生成模块发生错误时，用户仍应能返回聊天和原有业务页面、停用模块或恢复旧版本。

Agent 日常生成个人界面，不直接修改共享主站的源码与发布产物。主站与生成宿主本身的演进，继续通过项目开发和发布流程完成。

### 每个人自己的生成工作区

每位用户可以保存自己的工作台与模块组合。同一套家庭服务，可以呈现为不同的个人界面；某个用户采用新版本，不改变其他用户的布局或模块版本。

例如，用户可以提出：

> 帮我做一个晨间工作台：上面是今天需要我处理的日程，中间是三天内到期的食品，下面放发给我的家庭留言。食品按到期时间排序，可以打开详情。

Agent 先确认现有能力能否支持这些条件，生成候选工作台并展示预览。用户采用后，该工作台保留；随后说“把食品放在最前面，留言折叠起来”，Agent 基于已有版本生成修改。

工作台展示的数据持续从授权业务接口获取，不把生成时的数据快照当成长期真实状态。业务按钮由程序执行确定的操作，无需每次点击都再次请求模型。

### 使用过程

1. 用户描述目标，Agent 读取当前工作区版本和可用能力说明。
2. 缺少关键业务条件时澄清；缺少真实能力时说明限制，不生成虚构功能。
3. Agent 在独立工作区生成候选配置或模块。
4. 宿主完成适用的结构校验、构建和交互检查，保留检查结果。
5. 用户预览变化，决定采用、继续调整或丢弃。
6. 采用后持久保存版本与所属用户，后续直接运行已生成的程序。
7. 发生问题时可停用或恢复兼容的旧版本，并显示真实失败原因。

生成与预览不应自动写入真实业务数据。需要测试写操作时，使用隔离测试数据或模拟服务；预览中的真实写入必须明确进入正常业务操作流程。

## 与现有架构的关系

以下为 2026 年 10 月 29 日静态代码核对所得，不代表运行环境或真实模型流程已经验证。

| 层次 | 当前基础 | 对该方向的作用与缺口 |
| --- | --- | --- |
| 数据与业务服务 | 事项、留言板、资料、记忆等独立服务与存储 | 可以复用业务数据，具体接口的适配范围仍需逐项确认 |
| 可信规则 | 服务端身份校验、对象权限、版本检查、事项时效规则 | 生成界面继续受同一规则约束；不能自行授予权限或绕过裁决 |
| Agent 运行时 | 工具注册、按需加载、执行循环、审批、checkpoint | 可以接入生成和发布工具；现有运行 checkpoint 不等于模块版本管理 |
| 交互卡片 | `ui_blocks`、`InteractiveCardHost`、领域适配器 | 可以复用入口与真实资源交互经验；当前仅支持已注册类型，不加载任意代码 |
| 个人布局 | 固定类型小组件、尺寸与顺序配置 | 可以作为组合式工作台起点；当前配置保存在本机浏览器，不能生成新组件 |
| 前端构建 | Vite、React、TypeScript 与静态产物部署 | 可复用技术栈；需要新增生成模块的构建、隔离加载与发布机制 |

当前文件工具将写入范围限定在生成文件目录，Web 按账号隔离输出，不能直接修改 `web-react/src`。Web 不提供通用 Shell；CLI 的执行器也围绕生成目录配置。不能把“增加提示词”或“通过一次审批”当成已经获得前端开发与发布能力。

现有工具插件负责向 Agent 提供能力，前端模块宿主负责加载和运行界面，两者需要分别设计。

## 建议的架构分工

```text
用户需求 → 项目内 Agent → 候选工作区 → 校验与隔离构建 → 预览
                                                       ↓
稳定主界面 ← 个人工作区宿主 ← 按用户采用的模块版本
                    ↓
             受控业务能力桥接
                    ↓
        现有业务服务：身份、权限、规则、数据
```

### 能力契约

Agent 与生成程序需要发现可用的数据和操作。契约应包含业务含义、输入输出、权限、时间口径、分页或范围限制、版本要求、失败状态及实际支持的操作。

例如“今天需要我处理的日程”应复用现有事项语义，“三天内到期”要明确时区与日期边界。缺少有效期字段、查询能力或操作权限时，不把猜测包装成已支持功能。

OpenAPI 与现有前端 API 类型可以作为来源，但仍需要补充业务语义。工具执行入口和浏览器交互入口应共享业务服务与规则，不要求浏览器点击通过模型解释后才能完成操作。

### 生成工作区与构建器

Agent 只在被授权的候选目录写配置和模块源码。构建器使用受控依赖与隔离环境，限制文件、网络和资源访问，避免生成代码、构建脚本或依赖安装过程接触服务端凭据与家庭数据。

候选版本与正在使用的版本分离。构建失败保留诊断信息，旧版本继续工作。检查通过表示满足已执行的检查，不等于证明程序完全正确。

生成、检查、发布等能力应通过现有工具插件机制接入，遵守 [按任务加载工具约定](tool-loading.md)，保留用户与任务隔离、Skill 权限、审批及 checkpoint 恢复。

### 前端模块宿主与业务桥接

宿主负责加载模块、错误隔离、加载与失败状态、主题和设备适配，以及模块停用。具体实现需通过原型验证。

对任意生成的 JavaScript，优先评估独立来源或受限制 iframe 加消息桥接的运行方式。不能把任意生成代码直接作为受信任的主站同源组件加载，也不能把普通 iframe 自动视为充分隔离；来源、sandbox 权限、网络策略与消息校验需要共同设计。

生成模块不持有主站登录凭据，不接受模块自报的用户身份。宿主根据当前登录用户、模块声明和实际授权处理能力请求，校验消息来源、请求参数与响应范围；服务端再次执行业务权限和规则校验。

模块声明使用哪些能力，只表达需求，不代表获得授权。模块不得直接读取业务存储文件或调用未开放的内部能力。

### 持久化与版本管理

建议分别保存：

- 模块身份、所属用户、用途、所需能力与兼容要求；
- 不可变版本的配置或源码、构建产物、依赖和检查结果；
- 工作台布局、模块实例与当前采用的版本；
- 模块自身的偏好和必要状态，以及切换和失败记录。

工作区配置应由服务端按用户保存；浏览器缓存可以辅助加载。业务记录仍由原有服务管理，不复制成模块各自维护的另一份事项或留言账本。

多个会话或设备同时修改工作区时，需要版本检查，避免后一次保存静默覆盖前一次修改。跨设备采用策略、模块状态同步范围和兼容策略留待原型阶段决定。

恢复旧界面版本不撤销已经完成的业务操作。若未来允许模块状态迁移，必须独立设计兼容与恢复；首个验证范围应避免业务数据迁移。

## 可选的探索路径

以下阶段用于逐步验证方向，没有排期承诺。

| 阶段 | 验证目标 | 边界 |
| --- | --- | --- |
| 组合式工作台 | Agent 根据自然语言组合现有组件、数据绑定与布局，保存为个人版本 | 不能生成新组件，重点验证需求到可用工作台的闭环 |
| 生成新模块 | Agent 编写新的 React/TypeScript 界面，在独立环境构建、预览并采用 | 优先读取已有数据，不增加业务存储和迁移 |
| 可操作的个人工具 | 新模块通过桥接执行现有业务动作，支持继续修改与恢复 | 权限、并发、幂等和结果回执由可信服务保证 |
| 长期使用与维护 | 验证接口变化、依赖维护、跨设备使用和故障恢复 | 定时运行、外部集成、共享模块等另行评估 |

首个值得验证的场景是“晨间工作台”：读取用户可见的日程、临期食品和家庭留言，生成个人页面，采用后再次用自然语言调整。它同时覆盖跨业务组合、个人差异、持久保存和持续修改，又能优先复用现有服务。

首个完整原型还应至少包含一次现有固定组件无法直接表达的界面生成，避免只证明布局配置可行，却未验证生成新模块的路径。

## 判断是否值得继续的依据

- 用户能通过项目内 Agent 完成需求、候选、预览、采用和再次修改，不需要手工修改主站源码。
- 不同用户的布局和采用版本互不影响，权限撤销后不能继续读取原数据。
- 页面读取真实授权数据，操作结果来自业务回执，离线、冲突、无权限和部分失败能够正确展示。
- 模块生成或运行失败不会阻断主界面，旧版本可继续使用；恢复界面不会被误认为撤销业务操作。
- 生成成果能够跨会话保存和复用；稳定功能不需要每次重新生成，普通按钮操作不额外调用模型。
- 用户愿意持续保留和调整这些工具，生成耗时、成本与维护负担相对实际收益可以接受。

如进入实现，验证需覆盖最终模型请求、原生工具调用、生成产物、浏览器交互和持久化结果。真实模型与联网验证应限定次数与操作范围，区分模拟验证、真实服务验证和部署状态。

## 尚未确定的问题

- 工作区作为独立页面，还是嵌入现有家庭首页；手机端如何呈现。
- 配置式界面与任意代码模块的分界，首个原型采用哪种范围。
- 能力目录、前端 SDK 与业务 API 类型如何保持一致和版本兼容。
- 隔离宿主、受控依赖与构建环境的具体技术选择。
- 工作台跨设备同步、离线只读和主站 PWA 缓存如何配合。
- 长期模块状态、接口退役、资源额度与维护责任如何处理。
- 是否允许用户分享模块；如果允许，接收方需重新校验与授权，不能继承作者的数据或权限。

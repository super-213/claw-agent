# iPhone PWA 改造计划

日期：2026 年 10 月 26 日  
状态：主要代码已实施，本地自动验收通过；待服务器部署及 iPhone 真机验收  
目标：复用 React 前端和 FastAPI 后端，把现有网站做成可添加到 iPhone 主屏幕的 Web App，重点改善显示面积、键盘遮挡、滚动、照片上传和触控手势。

用户通过二维码打开网站，在 Safari 中选择“添加到主屏幕”，以后直接从桌面图标进入独立窗口。二维码承载网站链接；添加动作仍由用户确认。项目继续部署在现有服务器，更新通过网站发布，无需 Apple 开发者账号或 App Store 审核。

## 1 产品范围

### 首版交付

- 完整的桌面图标、名称、启动入口、独立窗口模式和安装引导。
- iPhone 竖屏优先，同时兼容横屏、Safari 普通页面和桌面浏览器。
- 聊天输入框随可视区域调整，兼容中文输入法、多行输入和键盘反复收起。
- 阅读历史时保持位置；流式输出、图片加载和弹层开关不会意外把页面拉到底部。
- 明确区分拍照、选照片和选文件，提供预览、上传状态、取消与失败重试。
- 附件操作面板和适合的移动弹层支持下拉关闭，保留返回和关闭按钮。
- 可控的静态资源缓存、离线提示和版本更新，聊天或上传期间不强制刷新。
- 完成真实 iPhone 上的安装、输入、滚动、照片及更新验收。

### 后续独立任务

- 锁屏或切后台后继续生成回答，并在回到前台时恢复结果。
- 主动推送、系统分享扩展和更复杂的手势导航。
- 离线业务查询、离线编辑和上传队列跨重启恢复。

本轮沿用当前事项不主动通知的产品规则。离线时展示明确状态；聊天、资料、事项等服务端操作仍要求联网。App Clip 和 Swift 原生客户端不在本轮实施范围；历史 [007 Swift 原生前端需求](007-swift-native-frontend-requirements.md) 保留，当前移动端建设以本文为准。

## 3 实施阶段

### 阶段一 建立真机基线和安装入口

1. 用当前生产 HTTPS 域名记录 iPhone Safari 的问题，至少覆盖聊天、家庭首页、资料详情及带输入框的弹层；记录机型、iOS 版本、页面和复现步骤。
2. 对同一设备比较 Safari 页面和主屏幕独立窗口，测量主内容可见高度，确认浏览器工具栏移除后的收益。
3. 保持现有 `/home` 启动路径；已登录进入首页，未登录进入登录页，完成登录后返回原本目标。启动页与深链接均通过现有路由和权限检查。
4. 补 Manifest 的稳定 `id`；沿用现有产品名称，补 192 和 512 像素 PNG 图标、独立的 maskable 图标以及 180 像素 `apple-touch-icon`。不要只依赖 SVG。
5. 在支持入口增加“添加到主屏幕”说明；按系统实际菜单展示步骤，在提供“作为 Web App 打开”开关的版本上提醒保持开启。已处于独立窗口时隐藏安装引导。
6. 二维码指向同一 HTTPS 域名下的安装引导页，例如 `/install`，离线本地生成二维码，不把登录凭据写入链接。已安装用户可以直接进入首页；微信等内置浏览器提供在 Safari 打开的说明，不承诺自动跳转。
7. 复用“记住登录”机制，分别验证 Safari 和独立窗口的登录、过期、退出及服务重启。不要假设两个环境会自动共享登录状态，也不要把密码转存到浏览器本地存储。

**验收条件**：首次用户能按页面说明完成添加；桌面图标和名称正确；从图标启动没有普通浏览器地址栏；重开、直接访问子页面和未登录访问均进入正确页面。

### 阶段二 处理键盘和滚动

1. 明确每个页面的主滚动区域：聊天由消息列表滚动，外层占满可视区域；输入区保持在可视区域底部。移动弹层由内容区滚动，标题和操作区按需固定。
2. 提取共用的移动可视区域处理，采用 `100dvh` 作为基础，在需要时使用 VisualViewport 的高度及偏移量修正；事件处理用 `requestAnimationFrame` 合并，并在卸载时清理。
3. 重新核对现有延时 `scrollTo(0, 0)` 补偿：只在真机证明需要的场景保留，避免与浏览器输入框定位、页面滚动恢复互相干扰。不要同时用减小高度和额外底部位移重复扣除键盘空间。
4. 输入框使用适合手机的字号，避免聚焦时意外缩放；保留用户手动缩放能力。兼容中文拼音候选栏、表情键盘、听写、外接键盘和横竖屏切换。
5. 多行输入达到高度上限后允许输入框内部滚动；最后一行、发送按钮和附件按钮始终可操作。
6. 保留接近底部时自动跟随输出的机制；用户上滑阅读后暂停跟随，出现“回到最新消息”入口。图片解码、附件预览展开及键盘变化时，按当前阅读状态保持锚点或继续跟随。
7. 同一会话临时离开再返回时恢复阅读位置；首次打开其他会话按既定规则展示最新内容，避免继承上一会话的滚动位置。
8. 打开弹层时锁定背景，关闭时恢复原有位置与焦点；弹层内长内容滚动到边界时不会带动后方聊天。
9. 减少手机端重复标题、外边距和占位，统一顶部与底部安全区，不在主屏幕模式下额外预留浏览器工具栏高度。

**验收条件**：连续开关键盘 10 次后没有遮挡、页面整体上移残留或底部空洞；生成过程中上滑读历史不被拉回；关闭弹层后回到原阅读位置；文字放大后主要按钮仍可见可用。

### 阶段三 优化照片上传

1. 点击附件按钮打开移动操作面板，提供“拍照”“选择照片”“选择文件”。照片入口使用合适的 `accept`，拍照入口可使用 `capture` 提示；具体相机和图库界面由 iOS 决定。
2. 上传前展示本地缩略图、文件名和大小，允许移除；选择取消时保留原输入和已选附件。
3. 每个附件区分待上传、处理中、上传中、成功和失败，失败后只重试该附件。成功附件继续复用后端现有媒体元数据，不重复上传。
4. 如果展示百分比，使用能获取真实上传进度的网络实现；无法获取时展示不确定进度，不使用模拟百分比。增加超时和用户取消，确保取消后不会挂住输入区。
5. 压缩仅用于聊天中的图片副本，按需降低像素和编码质量；保留文档、PDF 和资料原件。清楚告知用户何时发送的是压缩副本，避免影响长期资料的原件语义。
6. 使用真机拍摄照片、截图和 HEIC 样本验证解码、方向、预览和服务端识别。浏览器无法处理时走经验证的转换路径，或给出可操作的格式提示；不能只修改文件扩展名。
7. 检查连拍多图、大图和低内存场景；顺序或有限并发处理图片，及时释放 Object URL，避免同时解码全部大图。
8. 对齐代理和后端限制：当前 Nginx 请求体上限为 `20m`，聊天后端最多 10 个文件、单文件 25 MiB，批量上传会先受请求体总大小限制。实施时明确单文件和单次总大小，统一前端校验、代理配置及错误提示；覆盖 413 响应。
9. 登录过期或发送失败后保留当前文本与附件状态，提示重新登录或重试。恢复过程中沿用现有请求标识及去重约定，避免重复创建聊天消息。

**验收条件**：拍照、相册多选和普通文件上传均完成端到端操作；取消选择不清空草稿；网络失败后能重试；照片方向正确；超限、格式不支持及登录过期都有明确提示。

### 阶段四 增加有限且一致的手势

首批手势限定为附件操作面板、适合的详情弹层下拉关闭。横向切换页面、侧滑操作列表项等场景留待单独验证，不把所有页面改成自定义手势容器。

1. 拖动从面板把手或标题区域开始；内容区优先保持原生纵向滚动和文本选择。需要允许内容区下拉关闭时，只在内容已经滚到顶部且方向明确后接管。
2. 设置方向判定和移动阈值；使用 Pointer Events 处理捕获、取消及手指离开，拖动过程中面板跟随手指，松开后结合距离和速度决定关闭或回弹。
3. 动画可中断和反向操作，更新以 `transform` 和 `opacity` 为主；先复用轻量实现，必要时再引入与当前工程兼容的动效库。
4. 页面左右边缘优先留给系统返回手势；普通滚动、图片操作和按钮点击不触发面板关闭。
5. 沿用 `useDialog` 的历史记录与焦点管理，手势关闭和按钮关闭走同一条逻辑，防止重复退栈或退离当前应用。
6. 编辑未保存内容时，关闭需保留草稿或确认放弃；拍照、上传等进行中状态有明确处理。
7. 所有手势都有可见按钮替代；主要触控区域至少 44 CSS 像素。支持 VoiceOver、键盘操作和减少动态效果，不依赖震动作为唯一反馈。

**验收条件**：下拉面板可连续跟手、松开回弹、拖动取消及中途反向；长内容可以正常滚动；系统边缘返回、按钮、文本选择和未保存表单行为正确。

### 阶段五 完成缓存和更新机制

主屏幕安装与 Service Worker 分开验收：安装不等于离线可用，Service Worker 也不能保证页面在后台长期运行。

1. 在与当前 Vite 5 兼容的依赖版本中，选择 `vite-plugin-pwa` 的 `injectManifest` 方案，构建时注入带哈希的资源清单，保留可审查的自定义 Worker；注册入口由项目统一管理。
2. 生产环境在 HTTPS 下注册，开发环境默认关闭。沿用 `/sw.js` 路径与根作用域，先检查旧 Worker 和订阅状态；不要在每次启动时注销全部 Worker 或清除整个域名的缓存。
3. 只预缓存同源应用外壳、必要 JS/CSS、图标和离线提示页。账户、聊天、资料、事项 API、上传、下载及流式请求直接走网络，Worker 不缓存这些请求和响应。
4. 已安装且资源缓存完整时，离线进入能展示外壳及“当前离线，请联网后继续”的状态；尚未缓存的路径有简洁离线页。离线时禁止会产生业务写入的操作，已有输入留在当前页面。
5. Worker 不拦截 API、认证资源及文件路径为 SPA 页面；导航回退也只用于应用路由。外部字体不作为启动依赖，手机优先用系统字体，避免外部字体网络影响首屏。
6. HTML、Manifest、Worker 和哈希静态资源分开配置缓存策略：HTML 与 Worker 需及时重新验证，Manifest 可短缓存；带哈希的资源长期缓存。不存在的 JS、图标、Manifest 或 Worker 必须返回正确的失败响应，不能被 `try_files` 回退为 HTML。
7. 检测到新版本后显示轻量更新提示。聊天、上传或未保存表单存在时不强制刷新；用户选择更新后，先核对各已打开窗口的工作状态，再协调激活和刷新。不要仅根据当前页是否空闲自动执行 `skipWaiting`。
8. 检查草稿存储策略；至少提示用户保存或保留未发送文本后再更新。首版不为解决更新问题而默认把私有聊天和附件写入长期浏览器数据库。
9. 退出或切换账号时清理对应的内存状态及项目持有的私人临时数据，不把前一账号的缓存内容显示给下一账号；公共静态资源可继续复用。
10. 旧推送处理与本轮缓存更新分开处理，保留必要兼容且不新增订阅或权限弹窗，不恢复已停用的家庭提醒发送链。

**验收条件**：首次在线加载、已有缓存离线启动、重新联网和版本升级均可用；聊天中发布新版本不会丢失输入或中断请求；缓存清单中没有业务私有响应；两个窗口同时打开时更新不破坏另一个窗口的工作。

## 4 发布与回滚

继续沿用服务器、Nginx、FastAPI 和 HTTPS 域名。若由 Cloudflare Tunnel 提供外部 HTTPS，内部 Nginx 可以继续使用 HTTP；实际域名和证书在部署验收时核对，不把普通局域网 IP 的 HTTP 访问作为完整 PWA 验收环境。

1. 先发布到独立测试域名或隔离环境，使用可丢弃测试账号验证，避免测试 Worker 接管生产域名。
2. 明确构建版本，检查 `dist` 中 Worker、Manifest、图标及全部引用资源，再进行发布。
3. 改进当前直接复制静态文件的发布方式：先准备完整新资源，再切换 HTML 和 Worker；保留上一版哈希资源供仍在运行的旧页面使用，不能发布前先清空旧资源目录。
4. 同步检查 CDN 缓存规则，确保 HTML 和 Worker 不被长期缓存；修改 Nginx 后执行 `nginx -t`。
5. 在已有安装设备上完成升级，再验证首次访问设备；确认成功后更新正式二维码入口。
6. 回滚需同时恢复兼容的 HTML、静态资源和 Worker。为回滚构建生成新的缓存版本；不要只回退 HTML，也不要要求用户把“删除桌面图标并清空 Safari 数据”作为常规升级步骤。
7. 需要停用 Worker 时，在同一路径发布只清理本项目缓存并注销自身的恢复 Worker；保留足够的线上可达时间，让已有客户端有机会接收。恢复期间业务网站保持可访问。

部署文档补充安装说明、缓存排查、更新和恢复流程；[004 缓存策略](004-frontend-cache-busting.md) 与新的 Worker 策略一起更新。

## 5 验证清单

### 自动检查

- 运行现有 `npm run web:typecheck`、`npm run web:lint`、`npm run web:test` 和 `npm run web:build`，记录已有失败与新增问题。
- 为滚动跟随规则、附件取消重试、更新前的忙碌状态判断等关键行为添加必要测试，避免只验证实现细节。
- 通过生产构建的浏览器检查确认 Worker 安装、激活、离线回退和缓存范围；模拟网络失败、401、413 及两个窗口的版本更新。
- 如果调整上传接口或限制，同步运行对应的后端上传、权限和媒体处理测试。

### iPhone 真机检查

首版兼容目标为 iOS 17 及以上；先用实际设备确定可验证的版本范围，在验收记录中列明。至少覆盖一台较窄屏幕和一台带底部 Home 指示条的设备或可获得的等价组合。桌面模拟器和 Playwright WebKit 只作辅助。

| 场景 | 通过标准 |
| --- | --- |
| 扫码和添加 | 按引导完成添加，图标、名称、启动路由正确 |
| Safari 与独立窗口 | 两种入口都可用，独立窗口释放浏览器工具栏空间 |
| 中文与表情输入 | 候选栏、换行、粘贴长文本及键盘收起不遮挡输入和按钮 |
| 阅读与流式输出 | 看历史不被拖到底部；回到最新消息后恢复跟随 |
| 图片加载与屏幕旋转 | 阅读位置合理，布局不溢出，无残留大空白 |
| 照片和文件 | 拍照、多选、取消、方向、大图、失败重试和超限提示正确 |
| 弹层手势 | 拖动、回弹、取消、关闭和历史记录一致，内容正常滚动 |
| 登录与退出 | 重开遵循登录有效期，过期有提示，退出后看不到前一账号内容 |
| 离线与恢复联网 | 状态明确，无假成功，恢复后可继续业务操作 |
| 更新与回滚 | 打字、上传、生成及多个窗口场景无强制刷新和资源缺失 |
| 切后台与锁屏 | 不出现卡死的永久生成状态；需要恢复时明确提示当前状态 |
| 无障碍 | 放大文字、VoiceOver、减少动态效果及按钮替代操作可用 |

每个未通过项记录复现步骤、设备版本、截图或录屏和修复结果。键盘、滚动与照片三个核心问题必须在真机通过后才把首版标为完成。

## 6 实施顺序和完成定义

| 里程碑 | 内容 | 依赖 |
| --- | --- | --- |
| M1 安装与启动 | 阶段一，建立问题基线和完整安装路径 | 可访问的测试 HTTPS 域名 |
| M2 主要操作体验 | 阶段二和阶段三，解决键盘、滚动及照片上传 | M1 真机基线 |
| M3 手势与更新 | 阶段四和阶段五，完成有限手势、缓存及更新 | M2 稳定布局和明确的忙碌状态 |
| M4 发布验收 | 全部验证、部署、已有安装升级和回滚演练 | M1 至 M3 完成 |

每个里程碑保持可运行，先验证最影响日常使用的部分。首版完成指 M1 至 M4 全部通过，交付代码、图标、安装二维码、部署说明和真机验收记录；仅有桌面图标或 Lighthouse 分数不能代表体验目标完成。

当前 `services/chat_runner.py` 在流式连接被取消时会记录 `client_disconnected` 并中断执行。因此首版切后台验收只保证状态可理解、回到前台能重新核对会话，并明确提示中断；不能把它表述为后台持续生成。后续如要支持持续执行，应把任务从 HTTP 连接生命周期中分离，补任务查询、结果持久化、重连和重复操作防护，再单独制定后端实施计划。

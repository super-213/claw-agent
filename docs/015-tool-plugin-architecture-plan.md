# 工具插件化架构与渐进实施计划

日期：2026-10-29  
状态：P0–P4 已实施；本轮验证结果见第 12 节，P5 为可选增强。
依据：当前工作区代码及 `docs/tool-loading.md`；工具匹配数量与任务内保留数量不设硬上限。
目标：让新增普通工具通过独立插件包和启用配置接入，避免持续修改主入口、编排器和中央工具分类表。

## 1. 可行性与承诺范围

可行。当前已经具备工具定义、注册、原生 function calling、参数检查、审批、执行、结果回传和运行持久化机制，适合在其上增加插件发现与装配层，无须替换 Agent 主循环。

借鉴 Skill 的“目录 + 清单 + 自动发现 + 按需加载”模式，但工具插件需要额外解决可执行代码、依赖、身份绑定、权限、生命周期和恢复兼容性。Skill 提供使用说明与组合约束，工具插件提供可执行能力，两者独立注册、多对多引用。

本计划中的“即插即用”分两级：

- 首版：管理员放入可信插件包、配置依赖和凭据引用并启用，重启服务后自动发现；不编辑中央 Python 注册列表。
- 后续：管理员显式重载，通过完整校验后原子切换插件目录快照；不承诺任意 Python 模块无重启热更新。

插件仍需要实现工具代码。已有依赖和宿主能力能够满足的普通工具，应只新增插件目录、测试及启用配置。涉及新前端交互、新数据库结构、新宿主权限或服务适配的能力，仍可能需要对应代码与部署变更，不能承诺所有扩展都零改动。

## 2. 当前实现与实际耦合点

| 代码位置 | 已有基础 | 需要拆分的部分 |
| --- | --- | --- |
| `agent_runtime/models.py` | `ToolDefinition`、`ToolCall`、`ToolResult`、风险与执行选项 | 增加插件来源及版本等宿主元数据，不破坏模型工具协议 |
| `agent_runtime/registry.py` | 注册、别名、路由、参数检查、审批门控、超时与幂等重试 | 增加统一授权入口；明确插件 schema 支持范围 |
| `agent_runtime/builtin_tools.py` | 文件、时间、HTTP、Shell、Home Assistant 等工具 | schema、实现、依赖装配、别名集中在一个构建函数 |
| `agent_runtime/*_tools.py` | 家庭任务、留言板、知识库已各自拆文件 | 仍依赖主入口显式 import/register，以及手工注入业务上下文 |
| `web_app.py::_build_orchestrator` | 每次运行建立用户绑定的工具注册表 | 特殊处理文件读写、业务工具、MCP、上下文与回答钩子 |
| `main.py` | CLI 复用同一工具定义与执行器 | 与 Web 使用不同装配路径，插件发现应共用，启用范围可不同 |
| `agent_runtime/tool_loading.py` | `tool_load`、按运行加载 schema、Skill 工具白名单 | 分组依赖固定名称及前缀，新增类别可能修改中央表 |
| `core/orchestrator.py` | 完整模型—工具循环、检查点、审批及恢复 | 存在业务提示、回答守卫、资源事件，以及按 `family_` / `knowledge_` / `mcp_` 前缀选择历史结果复用行为 |
| `skills/registry.py` | 目录扫描、manifest、错误收集、重载、工具依赖声明 | 可参考发现方式；不能把 Skill 文本加载等同于可执行插件授权 |
| `agent_runtime/mcp_adapter.py` | 已有 stdio 外部工具接入与用户、工具白名单 | 纳入统一插件目录与策略；保留当前限制，不另造 MCP 客户端 |

补充事实：当前 `ToolDefinition.capabilities` 等字段不能直接视为通用权限已获执行器强制保障。部分约束实际由各 handler、业务服务和用户绑定逻辑执行，迁移前需逐项建立策略映射。

现有 MCP 仅接纳配置白名单内、带只读提示的工具，且执行时重新授权；配置由环境指定文件读取。它是已经可用的外部扩展路径，但尚不能代替本地业务插件生命周期与通用写入授权。

## 3. 建议结构

```text
tool_plugins/                         # 可执行插件，与 skills/ 分开
  datetime/
    plugin.json
    plugin.py
    README.md
    tests/
  files/
    plugin.json
    plugin.py
  family_tasks/
    plugin.json
    plugin.py
    hooks.py                          # 可选，迁移阶段引入
  weather/                            # 后续新增工具的示例包
    plugin.json
    plugin.py
    schemas/
      lookup.json
    tests/

agent_runtime/plugins/
  contracts.py                        # 插件清单、绑定上下文、来源记录
  discovery.py                        # 只读取清单，不执行插件代码
  manager.py                          # 校验、启用、装配、快照
  policy.py                           # 宿主权限裁决与执行前复核
  hooks.py                            # 业务扩展契约，迁移复杂工具时增加

config/tool-plugins.example.toml       # 可提交的配置样例
config/tool-plugins.toml               # 实际启用配置；凭据只存环境变量引用
skills/<skill>/manifest.json           # 继续使用 required_tools / allowed_tools
```

插件是同一领域的一组工具，不要求每个函数单独一个目录。schema 可以直接在插件代码中定义，也可拆到 JSON 文件；只保留一个定义来源，避免清单与代码重复维护。

运行时装配关系：

```text
扫描 plugin.json → 校验兼容性与管理员启用配置 → 导入可信入口
    → 创建插件目录快照 → 按本次用户/会话绑定 tools(context)
    → ToolRegistry → ToolLoadingSession → LLM 原生 function calling
    → 授权/参数/审批/执行 → ToolResult → 模型与运行持久化
```

`web_app.py` 与 `main.py` 最终仅调用共同的装配服务。宿主服务容器仍需维护，但普通插件不应要求为自己新增主入口分支。

## 4. 最小插件契约

以下是拟定接口，不表示当前已经实现。

### 4.1 清单

```json
{
  "id": "weather",
  "version": "1.0.0",
  "api_version": 1,
  "description": "查询指定城市天气",
  "entrypoint": "plugin.py:create_plugin",
  "runtimes": ["web", "cli"],
  "requires_services": ["public_http"],
  "requested_permissions": ["network:public-read"],
  "tool_metadata": {
    "weather_lookup": {
      "group": "weather",
      "keywords": ["天气", "气温", "weather"]
    }
  }
}
```

- 清单声明插件身份、兼容版本、宿主依赖和可搜索分类；具体参数由返回的 `ToolDefinition` 提供。
- `entrypoint` 必须位于该插件的规范化根目录内，禁止相对路径越界和符号链接逃逸。导入支持包内相对依赖，并用插件 ID/版本隔离模块名，避免多个 `plugin.py` 冲突。
- 发现阶段验证清单结构与路径，启用阶段才导入代码；被禁用或校验失败的插件不执行初始化。
- 清单、定义返回的工具、分类元数据、别名必须一致；保留 `tool_load`、`skill_load` 等控制名称。
- 普通新工具建议使用插件 ID 前缀；现有工具名与别名原样保留，避免破坏 Skill、历史运行和测试。

### 4.2 绑定与依赖注入

建议插件工厂接收显式宿主服务访问器，并通过 `tools(context) -> list[ToolDefinition]` 返回本次运行可用定义。

`ToolBindingContext` 提供用户与会话授权访问器、运行 ID、当前分支、已授权媒体访问器、用户文件访问器、审计入口及已批准的服务句柄。不会把整个 FastAPI Request、全局可变字典或全部环境变量交给插件。

- 身份、会话、文件所属用户等由宿主生成，模型参数不得覆盖。
- 共享插件实例只保存无用户状态的配置或客户端；用户、当前运行、已加载工具列表属于单次绑定，不能跨请求共享。
- 每次执行、审批继续和中断恢复时，重新读取当前身份及权限；不把持久化上下文当作仍有权限的证据。
- 依赖缺失、配置无效、服务不可用的插件显示明确诊断，不能让全站聊天启动失败。被宿主标为必需的基础插件失败时应阻止启动，不能静默降级安全约束。

## 5. 权限、Skill 和发现机制

插件接入与模型发现分两层：PluginManager 决定哪些能力安装并获准绑定；`tool_load` 决定本轮向模型提供哪些 schema。注册或被模型发现不等于获得执行授权。

执行许可由管理员配置、用户/家庭权限、会话权限、运行环境、Skill 工具约束和参数级审批共同决定；插件只能请求权限，不能自行授予权限。

必须保留以下现有边界：

- 文件读写仍通过规范化路径、受保护目录检查、上传来源与所属用户检查；不能仅依靠目录命名。
- 公网 HTTP 使用现有安全访问能力，保留内网、回环、重定向与 DNS 检查；Home Assistant 内网访问通过单独授权服务执行。
- Web 家庭模式继续禁用 Shell；CLI 的 Shell 仍受现有沙箱、路径和审批策略约束。
- 凭据通过宿主服务或限定的环境变量引用提供，不进入 schema、提示词、日志和工具输出。
- Skill 的 `allowed_tools` 只收窄可用集合，`required_tools` 缺失给出诊断；Skill 的权限声明不能开通插件或扩大宿主授权。
- 分类和关键词从插件元数据生成，不再依赖新增中央前缀判断。已有分组暂保兼容，分类文本使用受长度限制的可信插件信息。
- 执行器复核授权，不能只过滤发送给模型的 schema；模型直接猜出工具名也不能绕过权限。

本地 Python 插件属于可信代码扩展，进程内的服务访问约定不是安全沙箱。首版不接受用户上传任意插件代码；不可信第三方扩展需要独立进程或容器及真正的权限隔离。MCP stdio 的资源限制也不能宣称为完整隔离。

参数校验方面，当前内置检查器只支持 JSON Schema 子集，MCP 另有 Draft 2020-12 校验。P0 明确支持范围，P1 统一对插件采用 `jsonschema` 校验，并验证最终发送给现有模型 Provider 的 schema 兼容性，不能接受后在执行时忽略约束。

## 6. 业务扩展与通用主循环

只做目录扫描不足以完成复杂业务插件化。还要逐步迁移编排器中的这些职责：

| 当前职责 | 计划归属 |
| --- | --- |
| 任务、便笺、知识库上下文注入与重新授权 | 插件的上下文处理钩子 |
| 保存结果必须有工具证据的回答守卫 | 插件的回答校验钩子 |
| 校验前抑制模型文本流，避免先输出错误的“已保存” | 插件的输出缓冲需求 + 宿主统一流控制 |
| `resource_changed` 与卡片引用生成 | 插件结果适配；沿用已有事件和卡片协议 |
| 按工具名前缀决定历史结果能否复用 | 显式恢复策略与结果重验接口 |

钩子只在复杂业务迁移阶段加入，简单工具不必实现。宿主统一调度、限制次数与记录事件，插件不能重新实现模型循环或自行绕过审批。

钩子顺序在目录快照中固定；上下文处理、回答校验、展示适配分开。任一安全校验拒绝即阻止发布最终答案，后续钩子不能覆盖拒绝。错误进入明确失败或已有修复流程，不能无限重试，也不能静默跳过权限过滤。

移出业务判断时保持行为：旧卡片和资源事件不变、知识内容在权限变化后不被历史结果继续暴露、共享会话中的私人任务限制不变。

工具插件默认输出通用文本/结构化结果。新增交互卡片类型仍需要前端白名单适配器；首版不动态执行插件提供的前端脚本。

## 7. 生命周期、持久化与恢复

### 7.1 首版采用启动加载

- 管理员安装插件文件和依赖，启用后重启；运行中不自动 `pip install`，不从聊天上传目录扫描代码。
- 插件版本、内容摘要、配置修订与工具 schema 摘要进入目录快照和运行记录，凭据值不持久化。
- 重复插件 ID、工具名或别名冲突明确报错，不能按扫描顺序覆盖。
- 普通可选插件失败局部隔离，但错误不能泄露凭据。

### 7.2 恢复策略

- 每个工具显式声明历史结果复用/重新授权校验策略，副作用工具另声明幂等键支持；幂等重试、历史结果复用和权限重验是不同概念。
- 已完成的副作用不能因恢复或版本变化再次执行；保留现有工具执行账本及“不确定是否完成”的人工处理能力。
- 恢复时比对持久化版本、schema 与配置修订。插件缺失或不兼容时暂停并返回可解释状态，不能用新实现无提示重放旧参数。
- 旧运行缺少插件元数据时，内置兼容适配器沿用旧语义；未知插件不自动恢复。
- 等待审批期间权限撤回或插件停用：即使审批 token 有效，也拒绝执行；版本或审批策略变化后使原审批失效并重新确认。

进程内同步 handler 的超时不保证底层线程停止；非幂等操作超时后需要保留不确定状态，不能当作绝对未执行或自动重试。强制终止需要后续进程隔离执行后端。

### 7.3 后续重载

先构建并验证新快照，成功后供新运行使用；现有运行固定版本。管理员权限撤回立即在执行层生效，不能因旧快照继续执行。Python 实现变更首版仍要求重启；完全热更与依赖多版本隔离另行评估，不列入基础验收。

## 8. 分阶段实施

| 阶段 | 工作与主要改动位置 | 完成标准 |
| --- | --- | --- |
| P0：契约与行为基线 | 梳理全部现有工具、别名、Web/CLI 范围、权限检查、审批、恢复策略及业务钩子；确定清单与上下文契约 | 每项现有行为有迁移归属；不改变模型、工具名称和持久化行为 |
| P1：最小插件闭环 | 新建 `agent_runtime/plugins/`；目录发现、校验、启用配置、绑定、来源记录、动态分类与统一授权；抽取时间工具；接入 Web/CLI 装配 | 加入第二个简单插件，仅新增插件目录和配置即可被模型发现、调用并保存结果；禁用后不可执行 |
| P2：基础工具迁移 | 文件、HTTP、Home Assistant、Shell、Skill 桥接；把 Web 文件授权绑定移入宿主访问器和文件插件 | `builtin_tools.py` 变为兼容门面；Web/CLI 范围和全部文件/网络边界保持；不再按工具名替换 handler |
| P3：业务解耦 | 任务、留言板、知识库迁移；提取上下文、回答、展示和恢复策略扩展接口 | 编排器无需为新增业务工具添加前缀分支；原业务守卫、卡片和资源事件完整保留 |
| P4：统一 MCP 与运维 | 把现有 MCPAdapter 包装为一种工具来源；提供目录状态与校验命令；补齐示例、依赖安装和故障说明 | 当前 MCP 白名单、用户复核、只读范围及审计保持；接入已有兼容 MCP 服务不修改核心代码 |
| P5：可选增强 | 配置快照重载、插件状态管理界面、进程隔离、分发签名和依赖隔离 | 单独评审与验收；不作为 P1–P4 的前置条件 |

优先完成 P1，证明接入成本下降后再迁移复杂业务。不要同时重写业务服务、前端、存储和模型 Provider。

## 9. 验证与验收

测试验证完整链路，不以插件扫描成功或 prompt 中出现工具名作为完成依据。

1. **发现与装配**：有效、无效、禁用、依赖缺失、版本不兼容、路径越界、ID/名称/别名冲突；Web/CLI 环境差异；无用户状态串用。
2. **按需加载与原生调用**：检查最终 SDK 请求的 `tools`、名称、参数及 `tool_call_id`；模拟模型完成“发现→下一轮 schema→执行→tool 消息→最终回答”，检查持久化会话及 Run。
3. **授权与审批**：直接猜工具名、Skill 越权、伪造 actor、跨用户文件、共享会话、审批过期、禁用插件及撤销权限都不能执行；模型可见性不能代替执行授权。
4. **执行与恢复**：幂等工具重试、非幂等写入、线程超时后不确定状态、取消、重启、旧运行迁移、schema 变化、缺失插件；确认副作用不重复发生。
5. **业务回归**：任务/便笺创建证据、输出缓冲、资料权限重验、交互卡片、资源变更事件、分支和附件访问；验证最终回答而非仅工具函数返回。
6. **联网与真实模型**：实施时预设范围，建议先用本地可控服务完成协议验证，再限定一个测试插件、最多两次只读真实模型流程；不执行真实发信、支付、设备控制等副作用。未执行项如实记录。
7. **项目检查**：按阶段运行相关 pytest 与 Vitest；涉及前端时运行 typecheck/build；迁移完成再运行完整既有测试与安全检查。文档计划本身不代表这些检查已通过。

最终验收场景：在不编辑 `core/orchestrator.py`、`web_app.py`、`main.py`、`builtin_tools.py` 和中央分类表的情况下，添加一个使用已有宿主服务的普通插件，配置启用并重启后，Web/CLI 按支持范围发现它，模型完成原生调用，结果按原协议回传并持久化；禁用后直接调用和恢复调用均被拒绝。

## 10. 迁移与回退

- 分工具族迁移，一次只保留一个注册来源，防止旧注册和插件注册重复。
- 通过装配模式配置选择旧实现或插件实现；切换安排在重启边界，不在运行中的同一请求混用。
- 现有工具名、别名、ToolCall/ToolResult、NDJSON 事件与卡片结构保持兼容；新增持久化字段可选并带版本。
- 每阶段保留旧适配器和回归基线，验证后才移除门面。新插件创建且旧版无法识别的未完成 Run 不强行回退执行，保留记录并暂停恢复。

## 12. P2–P4 实施记录（2026-10-29）

### P2：基础工具插件与宿主服务

文件、公网 HTTP、Shell、Skill 桥接、显式浏览器/应用回调、Home Assistant 的定义均迁入 `tool_plugins/`。`builtin_tools.py` 的构建函数改为统一装配门面；原文件/网络/命令安全 helper 暂保兼容导出，保持既有安全测试的可替换边界。

新增 `FileToolAccess` 与 `foundation_services`：Web 不再按 `file_read` / `file_write` 名称替换 handler，用户文件目录、上传归属检查、生成链接及文件授权记录均在宿主访问器中处理。CLI 复用同一装配服务。Web 不注册 Shell；公网访问仍保留原内网限制与 Fake-IP 处理；设备实体白名单与控制审批保留。

宿主仅为当前代码库内已审核的内置包提供默认开关/权限基线；外部插件显式启用，并分别授予 `permissions` 与 `services`。插件收到的服务映射仅包含其清单声明且宿主批准的依赖。

### P3：业务插件与通用钩子

- 家庭任务、留言板、知识库的工具实现迁至各插件的 `tools.py`；原 `agent_runtime/*_tools.py` 保留旧 import 路径。
- 动态上下文、输出缓冲、回答证据守卫、来源补全、授权过滤、资源刷新与防止私有资料进入通用记忆的规则分别迁入插件扩展。
- 编排器使用通用钩子调度，不再 import 家庭任务/便笺/知识上下文模块，也不再按业务工具名前缀选择恢复方式。`family_task_context` 持久化字段为旧 Run 兼容暂保留，字段名不构成业务执行分支。
- `ToolDefinition.replay_policy` 显式决定结果复用；卡片由 `card_kind` 和 `card_resource_types` 声明，通用展示器继续清除任意 HTML/回调。
- 钩子按固定目录顺序组合，首个回答拒绝不可被后续钩子覆盖，最多两次修正；未通过则停止发布最终回答。
- 新增通用历史证据策略：未知、已移除或需要重新授权的历史工具不直接贡献旧结果或通用记忆。插件停用后不会因钩子消失而失去这条保护；持久化树与历史界面不改写。
- 迁移中发现的普通聊天和空回执回归已修复，证据见 [BUG-006](lessons-learned/BUG-006.md)。

### P4：MCP 统一来源与运维

`tool_plugins/mcp` 使用原 MCPAdapter 动态产生定义，不另造客户端。保留总开关、用户与工具白名单、只读限制、审批、资源限制、审计和不可信内容封装；增加来源配置摘要，参与恢复兼容检查。

新增 `scripts/tool_plugins.py list/validate` 和管理员 `GET /api/runtime/plugins`，提供不导入插件、不联系 MCP 的清单诊断。`GET /api/runtime/tools` 继续展示用户实际绑定的工具。发布包包含插件目录、诊断脚本和示例配置，不包含实际本地启用配置。开发与故障说明见 [插件开发文档](../tool_plugins/README.md)。

# BUG-029：开发启动脚本依赖 python 别名，状态脚本丢失推断端口

- 发现日期：2026-11-05
- 状态：代码已修复，脚本回归及实际开发服务启动、健康检查通过。

## 现象与影响
用户执行 `stop.sh` 后，`start.sh` 提示“未找到命令：python”。缺少状态文件时，`status.sh` 显示推断到 8000 端口，却提示缺少端口而跳过健康检查。开发脚本还容易与正式部署的 macOS 托管服务混淆。

## 复现条件
终端 PATH 有 python3、没有 python；项目已有可用 `.venv/bin/python`。没有 `log/service.env`，但仍有项目后端监听。

## 排查证据与原因
- 已确认 `start.sh` 检查并调用写死的 `python`；当前终端只有 python3，虚拟环境能够导入 fastapi 和 uvicorn。
- 已确认 `print_service` 推断的端口原来只用于显示，健康 URL 在推断前由空状态字段生成。
- `bash deploy/mac.sh status` 实际显示 API 与 Web 的 LaunchAgent 正在运行，网站和 API HTTP 200。后端父进程是 PID 1，部署配置含 KeepAlive。根目录开发脚本不管理这些服务注册；Vite 未运行不代表正式网站停机。

## 修复内容
启动时优先尊重 PYTHON_BIN，其次项目 .venv，再选择 python3/python；验证 Python 3.10+。状态检查在确认当前项目的单一监听端口后生成 URL，后端检查 `/api/health`，本地 curl 绕过代理。保留项目进程归属校验，不对多个监听端口随意猜测。

## 验证结果
`bash -n start.sh status.sh stop.sh` 通过；三项 Shell 回归覆盖带空格虚拟环境路径、仅 python3 的 PATH、显式无效配置不静默降级、推断端口用于 API 检查。实际 `STATUS_LOG_LINES=1 bash status.sh` 已显示后端 HTTP 200。没有运行 start/stop，也没有改变 LaunchAgent 注册。

## 后续预防及相关代码
正式部署用 `bash deploy/mac.sh status|start|stop|restart`；根目录 start/status/stop 面向 Python + Vite 开发服务。不要依赖交互终端的 python 别名。
相关：`start.sh`、`status.sh`、`deploy/mac.sh`、`test/test_local_service_scripts.py`。

## 2026-11-05 开发服务重启验证

按用户要求停止 macOS 托管服务后，通过修复后的 `./start.sh` 启动开发后端 8000 和 Vite 5173。状态文件成功写入；后端、前端和 Vite `/api/health` 代理均 HTTP 200。后端已加载修复，启动后超过一个 10 秒生命周期轮询周期未见新的解码错误。托管注册已卸载，但 plist 保留，下次用户登录仍可能自动启动。

## 2026-11-05 切回正式托管服务

用户澄清要求使用正式脚本。已执行 `./stop.sh` 停止开发后端和 Vite，再执行 `bash deploy/mac.sh start`。API、Web LaunchAgent 均 running，正式站点 8080 及其 API 健康检查均 HTTP 200；5173 无监听。最终运行模式为正式托管服务。

# BUG-002：上传路径别名在文件读取前未校验账号归属

- 发现日期：2026-10-29（Asia/Shanghai）
- 状态：已复现、修复并通过回归；运行服务尚未重启
- 影响范围：Web 账号绑定的 `file_read` 工具

## 现象与复现

按需加载工具的权限回归中，用两个合成账号分别创建上传文本文件。账号 A 的文件工具通过 `/generated/uploads/<账号 B>/notes.txt` 访问 B 的文件，修复前工具错误地返回成功。相同问题也涉及 `/files/` 别名。复现只使用临时目录和合成内容，没有读取真实账号文件。

## 证据与原因

`read_for_actor` 先把 `/generated/…` 当作磁盘路径计算，再检查路径是否位于生成目录以决定是否调用 `_authorize_generated_path`。此时路径尚未映射，因此没有进入归属检查。随后底层 `_file_read` 才把 Web 别名映射回真实生成目录，形成检查对象与实际读取对象不一致。

这是先前增加底层路径别名支持后，Web 权限封装没有同步适配的缺陷。它不是按需加载器授权了跨账号读取；加载器不决定文件归属权限。

## 修复

Web 文件读取遇到上传路径别名时，先用 `MediaInputReader.local_path` 解析、解码及规范化为真实文件路径，再执行 `_authorize_generated_path`，最后调用底层文件工具读取同一路径。项目文本文件仍沿原有路径处理和保护目录检查。

## 验证

新增 `test_loaded_file_tool_preserves_upload_ownership_for_web_aliases`：先加载文件工具，分别检查 `/generated/`、`/files/` 两种别名；自己的上传可读，其他账号未授权的上传返回 `file_not_found`。修复前该测试因跨账号读取成功而失败，修复后通过。包含该测试在内的本次相关后端回归合计 175 项通过。

## 后续预防

文件授权应针对最终将被读取的规范化路径。新增别名、解码或路径映射时，同时验证上层账号归属检查，不能只验证底层目录防越界。

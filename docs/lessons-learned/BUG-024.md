# BUG-024 手机已发布便笺显示图片暂不可用

- 发现日期：2026-10-30
- 状态：选图时序及HTTP成功后缓存阻塞已修复，新增小尺寸图片响应；50项前端/22项后端及真实JPEG生产SW故障模拟通过；前后端已更新，待手机确认

## 现象与影响
用户反馈发布便笺后图片显示“图片暂不可用”，无法查看图片。

## 复现条件
线上手机 Web App，便笺添加图片并发布后查看。用户已确认错误提示；用户确认标题为“1”、域名为 home-agent.zhihaojiang.com；实际失败请求状态尚待核实。

## 排查证据
- `BoardImage` 在原生 img 的 error 事件中显示该提示，不提供具体 HTTP 原因。
- 本机配置的数据目录 `.data/home/board.json` 检查时共 4 个已发布记录，图片块和资源记录均为 0。API 与 Nginx 日志中未找到 `/api/home/board/assets` 请求。未记录便笺正文、账号信息或完整日志。
- 隔离测试使用合成 PNG、三个测试成员和独立临时数据；发布后图片 HTTP 200，浏览器图片及大图预览解码成功；有权接收人可读，其他成员被拒绝。
- 按标题定位本机已发布便笺“1”，其中图片块为 0；再次检查没有图片接口请求。
- 从本机直接访问公网首页返回 Cloudflare HTTP 403，本机 Nginx 首页正常（200）。该证据仅说明本机请求被拒绝，不能证明手机图片也因相同规则被拒绝。
- 当前证据不能证明线上文件丢失、权限错误、代理错误或具体客户端问题，也不能断定手机请求到达的实例与当前检查实例一致。

## 补充：HTTP201后等待保存与图片加载过慢
用户随后反馈一直等待服务器保存、便笺图片几乎加载不出。

线上确认事实：API与Nginx记录上传POST201（2026-10-30 19:45:45 -0700），目录已有一份PNG及资产元数据；目录700且当前服务成功写入。网站/API健康检查200。未见该上传401/403，不支持目录或账号权限不足的判断。该PNG为2048×1536、3,094,751字节。

已确认客户端缺陷：uploadForm/jsonRequest/formRequest在成功HTTP响应后await离线缓存失效/保存；parseJson在401/403时也先await清缓存。本地IndexedDB无回调会使成功结果或授权错误无法送达UI；XHR此时已完成，不再触发网络超时，呈现长期等待。新增3个缓存维护永久不返回测试，在旧实现均失败，修复后通过。没有读取用户手机IndexedDB内部状态，因此不将模拟故障断言为手机的唯一根因。

修复：缓存维护在后台排队，网络结果不等待IndexedDB。账号owner与清理generation保留；业务失效改用按home/sessions/knowledge/interactive-cards分区的revision，防止取消等待后写入丢掉无关区域缓存，也防止旧的在途响应回填已失效区域。原有离线、跨账号及401/403回归保留并通过。

加载优化：保留受保护原始PNG与原端点语义；新增width=64..2048预览参数，每次仍先执行当前成员及便笺可见性授权。RGB输出JPEG82，透明图仍PNG；不生成持久派生文件，不放宽no-store，不引入撤权/到期后仍可读的共享缓存。UI缩略图640px、大图1600px。对线上同一源文件本机编码测得60,635字节与240,990字节，原文件仍保留；实际手机网络耗时未量测。

验证：50项前端（包含3项缓存永不完成、离线缓存及权限回归）、22项便笺后端通过。后端新增真实图像编码大小/尺寸、无权成员404、撤下后404及非法尺寸422测试。生产构建通过。隔离WebKit iPhone参数、生产SW且将页面IndexedDB.open设为永不回调，真实JPEG仍完成压缩、XHR取消重试、POST201、发布后刷新、640/1600图片GET200及大图解码；未向线上便笺写入测试记录。

运行状态：前端dist已更新；实际部署脚本restart成功，网站/API健康检查通过，后端width预览接口已加载。手机需点击更新加载新客户端，不要求先保存或关闭其他窗口。

## 原因
已确认代码缺陷：
- 待上传文件与失败状态只保存在 BoardFields 组件内；关闭重开丢失状态，可在未附上图片的情况下发布。编辑已有便笺时，首次上传完成前也没有标记本地编辑，重开会退回阅读状态。
- 上传回执没有校验 asset_id；缺少图片编号的回执也被当成成功并解除发布限制。
- 后端发布只校验资产记录与归属，没有验证对应图片文件存在，允许发布文件已缺失的图片引用。

未确认：手机那次原始操作是否触发以上路径；线上没有对应图片请求证据，不能将上述缺陷直接写成该次唯一根因。多图快速回执测试在原代码通过，不能宣称已复现多图丢失。

## 修复内容
- 在账号隔离的卡片内存状态中保留待上传文件与失败状态，关闭重开自动恢复；切换账号时统一清理。仅保留本次页面会话，不将图片写入 localStorage；刷新/关闭页面由未保存编辑提示保护，系统强制终止不保证恢复。
- 开始选图即标记编辑；图片上传完成且回执编号有效前禁止发布，上传与失败状态未解决时禁止重新读取丢弃编辑。
- 上传回执检查真实资源编号格式；同步更新内容引用，避免连续上传依赖下一次渲染。
- 后端发布校验资源编号、归属及文件存在；缺失文件拒绝发布，重新上传后可按原请求重试。
- 已经发布且服务器未保存的图片无法凭空恢复，需要用户重新选择原图片。

补强 `scripts/validate_board.py`：记录图片接口响应状态，发布后检查缩略图和预览图 complete 与 naturalWidth，避免只验证图片按钮而误判展示成功。
